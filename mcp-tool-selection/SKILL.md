# MCP 工具选择与注册表设计

## 用途

指导 MCP 工具注册表的设计、改造和验收。核心是回答三个问题：工具该怎么组织、要不要上检索、怎么证明改动有效。

本 Skill 的推荐基于 2026-10 的一次实测：93/200/400/1000 四个规模、75 条标注任务、真实模型盲测、真实端点延迟测量。**若干被广泛推荐的常见做法在实测中是负收益**，见 `references/antipatterns.md`，动手前必读。

## 触发场景

- 工具数超过 50，开始考虑要不要做检索或分组
- 模型选错工具，需要定位是检索没召回还是选择判断错
- prompt 里塞工具 schema 导致 token 或延迟不可接受
- 要给现有工具库补描述、做去重、打标签
- 要建一套能回归的工具选择评测集

## 第一步：先量三个数，再谈方案

不要先选架构，先量这三个数。它们决定后面所有决策。

| 要量的 | 怎么量 | 用途 |
|---|---|---|
| **工具总数 N** | 数注册表条目 | < 100 通常不需要检索 |
| **schema token/次** | 序列化全部工具定义后估算 | 乘 agent 平均步数 = 真实输入成本 |
| **近义工具密度** | 同一业务对象上有几个工具做增删改查 | **真实难度的唯一来源**，比总数重要得多 |

近义密度的算法：按业务对象分组（体重、饮食打卡、菜品…），统计每组有几个工具。**同对象上的动作变体 ≥ 4 个时，这里就是模型出错的地方。**

## 决策树

```
工具总数 N 与近义密度
  │
  ├─ N < 100 且近义组 ≤ 3 个工具
  │     → 全量暴露，不要上检索
  │       实测：93 个工具全量暴露 96.7%，加检索反而掉到 83.3%
  │
  ├─ N < 100 但近义组 ≥ 4 个工具
  │     → 先合并/重命名重复工具，再评估。架构救不了近义混淆
  │
  └─ N ≥ 200，或 schema token 已超 10k/次
        → 上单级检索，但必须先做工具卡（工作流第 2 步）
          实测：无卡召回 86.7%，有卡 100%
```

## 五步工作流

### 第 1 步：清点与去重（收益最高，成本最低）

找出功能重叠的工具并合并或改名。典型症状是同一件事有两个工具都能做。

**判断方法**：写出「用户会怎么说这件事」。如果这句话能匹配到两个以上工具，它们就该合并，或明确区分（一个记体重、一个记打卡，要在名字和描述里说清差别）。

实测中有一条任务，所有方案（全量、检索）全部选错，原因就是两个工具都能记体重。**这类损失任何架构都救不回来。**

### 第 2 步：给每个工具生成工具卡（吃掉绝大部分收益）

工具卡是给检索用的索引文本，格式：

```json
{
  "tool_name": {
    "zh": "一句话说明这个工具做什么，用人话说，不要复述函数名",
    "queries": ["用户可能怎么问 1", "...共 5~8 条，覆盖不同说法与口语化表达"]
  }
}
```

生成方法见 `scripts/gen_tool_cards.py`，规范见 `references/tool-card-spec.md`。

**关键要求**：
- 只喂工具的 name / namespace / 原始描述 / 参数，**绝对不要喂评测任务**，否则是拟合
- 至少 5 条话术，覆盖「用户的口语表达」而非「开发者的术语」
- 用比目标模型更强的模型来生成

实测：仅这一步就让 1000 工具规模下召回从 86.7% 提到 100%，且不需要任何额外的融合或路由。

### 第 3 步：上单级检索

只用一层全局检索，固定 K。

```
query → 检索 top-K → 这 K 个 schema 进 prompt → 模型选择
```

- K = 10（实测 100% 召回的下限是 8，取 10 留一档余量）
- 检索用 BM25 即可；若加向量走混合检索，但**不要做三通道 RRF**（实测贡献为 0）
- **不要做两层级联**（bundle 路由 → 包内检索），实测是负收益
- **不要做分数断层自适应 K**，在 RRF 上不成立

### 第 4 步：建评测集（在第 3 步之前就该开始）

没有评测就没有优化方向。最小可用集：

- **50~100 条**任务，按 easy / medium / hard 分层
- 每条标注：用户原话、正确工具、难度
- **难度按语义距离标，不要按工具名重合度标**。判断方法：只看工具名不看描述，「设个晚上九点的提醒」→ `reminder_create` 排第 68 名，这是 hard
- 切 **dev / hold-out**：dev 调参，hold-out 只验收，绝不参与调整

### 第 5 步：分三层验收，不要只看端到端

端到端准确率无法定位问题。必须分开测：

| 指标 | 含义 | 合格线 |
|---|---|---|
| **recall@K** | 正确工具在不在候选集里 | ≥ 95%，否则先修检索 |
| **selection accuracy**（候选内） | 给了正确工具，模型选对没 | 与架构无关，看模型本身 |
| **端到端准确率** | 两者乘积 | 对外汇报用 |
| **TTFT** | 首 token 时间 | 与全量方案对比 |
| **schema token/次** | 输入成本 | 乘步数看总账 |

**召回不足时不要优化模型侧，那是在错误的地方使劲。**

## 关键阈值速查

| 项 | 值 | 来源 |
|---|---|---|
| 单级检索固定 K | 10（下限 8；K=6 → 97.8%，K=4 → 91%） | 实测 |
| 全量暴露可用的工具数 | < 100（93 个 96.7%，1000 个仍有 92%） | 实测 |
| 检索相比全量省 token | N=93 省 86%，N=1000 省 98.9% | 实测 |
| 检索相比全量降 TTFT | N=93 降 33%，N=1000 降 66% | 实测 |
| 本地 BM25 检索开销 | 1000 工具 4~8 ms | 实测 |
| prefill 边际成本 | 约 37 ms / 1000 工具（内网 27k tok/s 网关） | 实测 |
| 单步准确率 → 5 步任务 | 0.92⁵ ≈ 66%，0.96⁵ ≈ 82% | 幂次放大 |

## 一句话总结

**收益来自索引文本质量，不来自架构复杂度。** 先补工具卡、先去重，再谈检索；检索只做单级、只做固定 K。任何「按需加载 schema」的聪明设计，都不如把工具描述写好。
