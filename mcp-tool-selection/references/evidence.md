# 实验证据与适用边界

供说服他人或判断结论是否适用于自己场景时引用。

完整实验代码：`~/WorkBuddy/2026-10-29-10-22-01/mcp_rag_demo/`（93 个核心工具 + 扩容器 + 75 条任务 + 全部脚本）。
一页版结论：同目录下的 `FINAL_SUMMARY.md`。

---

## 1. 实验设置

| 维度 | 设置 |
|---|---|
| 工具规模 | 93 / 200 / 400 / 1000（严格嵌套），另有 284（200 + 84 个同域近义干扰） |
| 任务集 | 75 条标注任务，easy 25 / medium 30 / hard 20 |
| 数据切分 | dev 30 条调参，**hold-out 45 条只验收** |
| 检索器 | 纯 BM25，无 embedding、无向量库 |
| 选择模型 | `deepseek-v4.1-flash`，盲测 n=24（任务 id 打乱为随机串防对答案） |
| 延迟测量 | 真实端点，`qwen3.7-flash` 主测 + `qwen3.6-flash` / `qwen3.5-plus` 复测 |
| 对照方案 | 全量暴露 / 单级检索 / 两级+兜底 / 两级无兜底 / 拼接打分 / 工具卡增强 |

## 2. 检索层：召回与 token

hold-out 45 条，K=10：

| 工具数 | 全量 token | 全量召回 | 检索召回 | 检索 token | 节省 |
|---|---|---|---|---|---|
| 93 | 4,109 | 100% | **100%** | 586 | 85.7% |
| 200 | 9,995 | 100% | **100%** | 590 | 94.1% |
| 400 | 21,000 | 100% | **100%** | 589 | 97.2% |
| 1000 | 54,040 | 100% | **100%** | 591 | **98.9%** |

**候选数恒定 12.9，token 几乎不随规模增长。** 这是检索唯一真正重要的性质：把「工具数量」从成本函数里摘掉。

同域近义干扰压力测试（284 个工具，其中 84 个是同领域近义工具）：召回仍 100%。

---

## 3. 归因消融：收益来自哪一步（N=1000）

| 配置 | 召回率 |
|---|---|
| 有工具卡 + 三通道 RRF | **100%** |
| 有工具卡 + 单通道 BM25 | **100%** |
| 无工具卡（原始描述） | 86.7% |
| 两级 + 并集兜底 | 97.8% |
| 两级 + 无兜底 | 80.0% |

**三条结论**：

1. 全部收益来自工具卡。有卡就是 100%，加不加 RRF 一模一样。
2. 两级 bundle 路由是负收益。带兜底 97.8%，是全场唯一没到 100% 的方案。
3. 并集兜底必要（80% → 97.8%），但它只是在给 bundle 层擦屁股。

## 4. 模型侧：准确率

v1（无工具卡，93 工具，n=30）：

| 实验臂 | 召回 | 候选内 | 端到端 |
|---|---|---|---|
| 全量 | 100% | 96.7% | **96.7%** |
| 单级检索 K=10 | 90% | 92.6% | 83.3% |
| 两级 + 兜底 | 90% | 92.6% | 83.3% |

v2（有工具卡，n=24 hold-out）：

| 实验臂 | 端到端 | 正确数 | schema token |
|---|---|---|---|
| 全量 200 | 92% | 11/12 | 9,995 |
| 全量 400 | 92% | 22/24 | 21,000 |
| 全量 1000 | 92% | 22/24 | 54,040 |
| **检索 K=10** | **96%** | **23/24** | **591** |

**配对分析（必须看这个，不要只看百分比）**：

| | 条数 |
|---|---|
| 两臂答案完全相同 | **23 / 24** |
| 只检索对 | 1 |
| 只全量对 | 0 |

McNemar **p = 1.000**。24 条里只有 1 条能区分两个方案。**所以能站住的结论是「检索不劣于全量」，不是「检索更准」。**

**准确率这块的真实结论**：
- 全量暴露在 1000 工具规模下**没有崩**（92%，与 200 工具时相同）
- 检索没有让它变差，也没有显著变好
- 真正的差别在 token 和延迟

## 5. 延迟

本地检索（纯 CPU）：

| 工具数 | 建索引 | 单次检索 p50 |
|---|---|---|
| 93 | 17 ms | 0.5 ms |
| 1000 | 77 ms | 4.3 ms |

模型侧 TTFT（真实端点，流式，5 次中位数，关闭思考模式）：

| 工具数 | prompt token | 全量 TTFT | 检索 TTFT | 降幅 |
|---|---|---|---|---|
| 93 | 3,451 | 0.67 s | 0.45 s | 33% |
| 200 | 5,898 | 0.77 s | 0.45 s | 42% |
| 400 | 10,460 | 0.83 s | 0.45 s | 46% |
| 1000 | 24,000 | 1.32 s | 0.45 s | **66%** |

拆开：固定开销约 0.43 s，其余是 prefill，边际吞吐约 27,000 token/s，即**每 1000 个工具多付 37 ms**。

跨 3 个模型复测（qwen3.7/3.6-flash、qwen3.5-plus），曲线方向一致，倍数 1.4×~2.9×，说明这是**prompt 长度的结构性效应**，不是模型特性。

## 6. 适用边界（重要）

以下条件变化时，上面的数字**不能直接套用**：

| 条件 | 影响 |
|---|---|
| **工具描述质量差** | 全量暴露会显著变差。本次核心 93 个工具的描述是精心写的，v1 里故意留 21.5% 空转描述时召回只有 86.7% |
| **选择模型更弱** | 「1000 个不崩」可能只是 deepseek-v4.1-flash 的特性。未在更弱模型上验证 |
| **真实 schema 复杂度** | 本次候选清单是「工具名 + 一句中文说明」的极简格式。真实 MCP schema 有几十个参数、嵌套 JSON，干扰更强 |
| **多步任务** | 单步 92% 在 5 步任务是 66%，在 8 步是 51%。本次只测了单步 |
| **公网 API** | 本次是内网网关（固定开销 0.43 s、27k tok/s）。公网叠加 RTT 和排队后，差距只会**更明显** |
| **prompt 缓存** | 全量前缀可缓存（每步相同），检索候选每步变（缓存收益近零）。开缓存会**缩小**延迟差距和价格差距 |
| **模糊任务** | 本次 75 条任务都是「唯一正解」。真实场景大量是「两个工具都能做」，本次未覆盖（唯一的例子是两个工具都能记体重，所有方案全错） |

## 7. 与公开研究的对照

| 研究 | 结论 | 与本实验的关系 |
|---|---|---|
| 生产遥测（arXiv 2606.30317） | 工具数 10 → 50 时，Haiku 95% → 65%，Sonnet 98% → 78% | 与本实验的「100 个以上不崩」冲突。差异可能在**候选清单的渲染格式**：该研究把完整 schema 放进 prompt，本实验用极简描述 |
| 跨客户端实测（2026-10，3,336 次） | Claude Code / Codex / Antigravity 在 100 工具下每轮全对 | **一致**。原因是这些客户端只暴露工具名，schema 按需加载 |
| RAG-MCP（arXiv 2505.03275） | 全 schema 13.62% → 检索分桶 43.13% | 方向一致。注意该论文统计的是 prompt 里 **MCP 服务器个数**，不是工具个数，常被误传 |
| BFCL 370 工具 | 固定 K=5 覆盖 64.7%，自适应平均 K=7 覆盖 90.3% | **不一致**。本实验 K=8 即 100%，因为工具卡让语义匹配大幅变易 |

**结论**：本实验的数字比公开研究乐观，最可能的原因是**候选清单的渲染格式更简洁**。迁移到真实 schema 时，应以悲观一侧为准。
