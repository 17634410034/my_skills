# 反模式：被实测推翻的做法

以下每一条都是「听起来合理、社区常见、实测无效或负收益」的做法。动手前逐条对照。

来源：2026-10 实验，1000 工具规模、hold-out 45 条任务、真实模型盲测。

---

## ⛔ 反模式 1：做两层级联（bundle 路由 → 包内检索）

**常见说法**：「先用工具包做粗粒度路由，命中后在包内细粒度检索，把选择问题转化成路由问题。」

**实测结果（N=1000，hold-out 45 条）**：

| 方案 | 召回率 |
|---|---|
| 单级检索（有工具卡） | **100%** |
| 两级 + 并集兜底 | 97.8% |
| 两级 + 无兜底 | **80.0%** |

**两级是负收益。** 加上并集兜底也只能到 97.8%，是全场唯一没到 100% 的方案；去掉兜底直接掉到 80%。bundle 层的净贡献是**一次单点故障**——包路由错了，后面全错，没有任何补救路径。

**替代方案**：单级全局检索 + 固定 K=10。工具的命名空间信息直接拼进索引文本，让检索器自己利用，不要做成一层独立的打分与截断。

**什么时候才考虑分层**：单级召回实测低于 95%，且已确认瓶颈是「候选池太大」而非「索引文本质量差」。此时分层也必须带并集兜底。

---

## ⛔ 反模式 2：做分数断层自适应 K

**常见说法**：「top1 与 top2 分数差很大就只给 3 个，分数接近就给 20 个，省 token 还更准。」

**实测结果**：在 RRF 融合下**完全不触发**。阈值从 0.05 扫到 0.40，候选数几乎是常数。

原因是 RRF 的分数形状是 `1/(60+rank)` 型衰减：第 1 名到第 20 名的相对差距只有十几个百分点，曲线平滑，没有任何「断层」可用。阈值调严了永远不触发，调松了等于没截断。

**替代方案**：固定 K=10。

**如果确实要自适应**：只能对**原始 BM25 分数**做拐点检测（BM25 分数确实有断层），不要对 RRF 分数做。

---

## ⛔ 反模式 3：多通道 RRF 融合

**常见说法**：「全字段、仅工具名、仅中文话术三路打分，按名次融合更稳。」

**实测结果**：**贡献为 0。**

| 配置 | 召回率（N=1000） |
|---|---|
| 有工具卡 + 三通道 RRF | 100% |
| 有工具卡 + 单通道 BM25 | **100%** |
| 无工具卡 + 任意融合 | 86.7% |

有卡就是 100%，加不加融合一模一样。**收益 100% 来自索引文本，不来自融合策略。** 多通道要维护三套索引、三套参数，换来 0 收益。

**替代方案**：单通道 BM25，把精力全投到工具卡上。

**例外**：如果你的查询里既有中文口语又有工具名/参数这类强关键词，混合检索（BM25 + 向量）可能值得，但那是「两种模态」而不是「三路同质通道」，性质不同。

## ⛔ 反模式 4：把包描述拼接成一段长文本会「稀释」

**常见说法**：「包级索引应该用 profile + 成员最高分加权，拼接全部成员描述会导致长文稀释，稀释精确匹配的包。」

**实测结果**：**未复现，方向相反。** 拼接臂全程 ≥ 加权打分臂，在描述降级条件下还更好（53.3% vs 50.7%）。

原因：拼接把**成员工具名**带进了包级索引，而工具名是极强的关键词信号。

**结论**：如果必须做包级索引（不推荐，见反模式 1），**要在 profile 里显式加入成员工具名**，不要只用一句概括描述。

---

## ⛔ 反模式 5：用「工具数量」来论证需要 RAG

**常见说法**：「工具涨到 1000 个，模型肯定选不过来，所以要上检索。」

**实测结果**：工具数从 200 涨到 1000，准确率**完全不变**（都是 22/24）。

关键证据：全量 1000 臂的 2 条错误**全部落在核心 93 个工具内部**，没有一条被 900 多个跨域干扰工具带偏。

**「工具数量」本身不构成难度，「近义工具密度」才构成。** 模型在大量无关项里定位一个语义对口工具的能力非常强；它会翻车的地方是「三五个长得几乎一样的工具里选哪个」。

**替代方案**：先量近义密度（同一业务对象上有几个动作变体），再决定要不要 RAG。

---

## ⛔ 反模式 6：OCR 式描述（`xxx 平台的 yyy 操作`）

**常见症状**：工具描述是「`grafana` 平台的 `create alert` 操作」这种把函数名翻译一遍的文本。

**实测结果**：这类空转描述占 93 个工具里的 20 个（21.5%），**直接导致召回从 100% 掉到 86.7%**。中文查询「把告警规则建一条」在这段文本里一个词都对不上，正确工具被排到 **76~92 名**（共 93 个）。

**这是所有失败里最主要的一个原因，也是最好修的。**

**替代方案**：见 `tool-card-spec.md`。描述要写「用户会怎么说这件事」，不是「这个函数叫什么」。

---

## ⛔ 反模式 7：把检索做成远程调用

**实测结果**：

| 规模 | 全量 vs 检索省下的 TTFT | 检索能容忍的最大延迟 |
|---|---|---|
| N=30 | ~50 ms | 50 ms |
| N=93 | ~220 ms | 220 ms |
| N=1000 | ~870 ms | 870 ms |

本地 BM25 检索 1000 工具只要 4~8 ms，完全安全。但换成远程向量库（30~80 ms RTT），**在工具数少的时候会把省下的时间全部吃回去**。

**替代方案**：索引和检索放在同一进程或同一台机器；工具数 < 100 时根本不要上检索。

---

## ⛔ 反模式 8：用「端到端准确率」验收架构改动

**为什么不行**：端到端 = 召回率 × 候选内准确率。两个因子任一变化都会影响结果，只看端到端无法定位该修哪一层。

实测中同一个端到端下滑，拆开后是「3 条检索没召回 + 1 条模型选错」，**修的方向完全不同**。

**替代方案**：分三层测（recall@K / selection accuracy / 端到端），见 SKILL.md 第 5 步。

---

## 附：被推翻的「直觉」

| 直觉 | 实测 |
|---|---|
| 候选少了模型会更准 | **没有证据**。全量臂候选内准确率 96.7%，检索臂 92.6%，反而略低 |
| 模型在 100 个工具以上会开始崩 | 93 个 96.7%，1000 个 92%，没有明显崩塌 |
| 多一层抽象更稳 | 多一层 = 多一个单点故障，实测掉 20 个点 |
| 融合多路信号更鲁棒 | 在索引质量已经足够时，融合贡献为 0 |
