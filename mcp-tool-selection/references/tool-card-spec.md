# 工具卡规范

工具卡是给检索用的索引文本，与工具的 schema 分开维护。它不参与模型调用，只参与检索。

**实测价值**：1000 工具规模下，召回从 86.7%（只有原始描述）提升到 100%（有工具卡）。这是整套方案里唯一被证明有效的单一改动。

---

## 1. 数据结构

```json
{
  "food_search_by_keyword": {
    "zh": "按关键词搜索食物，返回名称、热量和营养成分，用于不知道具体是哪一种食物时",
    "queries": [
      "鸡胸肉多少卡",
      "帮我查一下这个东西的热量",
      "有没有低脂高蛋白的食物推荐",
      "我想知道一份米饭大概多少大卡",
      "这个能不能吃",
      "搜一下西兰花"
    ]
  }
}
```

| 字段 | 要求 |
|---|---|
| `zh` | 1 句，说清「做什么 + 什么场景用 + 与同类工具的区别」。不超过 60 字 |
| `queries` | 5~8 条。用户口语，不是开发者术语 |

---

## 2. 质量判据：好与坏

### ❌ 坏例子（这类描述是召回失败的根因）

```json
{
  "grafana_create_alert": {
    "zh": "grafana 平台的 create alert 操作",
    "queries": ["create alert", "调用 grafana_create_alert", "创建告警"]
  }
}
```

问题：
- `zh` 只是把函数名翻译了一遍，**没有任何场景信息**
- `queries` 是术语而非用户话术。真实用户说的是「把告警规则建一条」「这个指标超了给我说一声」
- 结果：中文查询一个词都对不上，该工具被排到 76~92 名（共 93 个）

### ✅ 好例子

```json
{
  "grafana_create_alert": {
    "zh": "为监控指标创建告警规则，当指标超过设定阈值时触发通知",
    "queries": [
      "把告警规则建一条",
      "这个指标超了给我说一声",
      "CPU 超过 80% 就提醒我",
      "帮我配个监控，磁盘满了要报警",
      "给订单服务的错误率设个预警"
    ]
  }
}
```

差别在于：**好例子能让人在不看函数名的前提下知道什么时候该用它。**

## 3. 生成提示词模板

```
你在为一个 MCP 工具库做「工具卡增强」，目的是让工具检索能听懂用户的自然语言。

下面每个工具给出 name / 所属领域 / 现有描述 / 参数。很多描述是空转的（比如
「xxx 平台的 yyy 操作」），完全看不出该在什么时候用它。请为每个工具产出：
  1. zh：一句中文说明「这个工具到底做什么、什么场景该调用它」，要能与同类工具区分开；
  2. queries：6 条用户可能的口语化说法，要有真实语气（例如「帮我把这个删了」），
     不要出现工具名里的英文单词，不要写成「调用 xx 工具」这种说明腔。

严格输出一个 JSON 对象，键是工具 name，值是 {"zh": "...", "queries": ["...", ...]}。
不要 markdown 代码块，不要注释，不要多余文字。

=== 工具清单 ===

[grafana_create_alert] 领域=ops  参数=metric, threshold, window
  现有描述: grafana 平台的 create alert 操作
  现有别名: 创建告警 / 告警设置
```

### 关键约束

1. **只喂 name / namespace / 原始描述 / 参数。绝对不要喂评测任务。** 喂了就是数据泄漏，召回率会虚高，上线后崩。
2. **queries 里禁止出现工具名中的英文词。** 否则这些卡片只对英文查询有效，而真实用户说中文。
3. **要求「与同类工具区分开」。** 这是让 `body_weight_record` 和 `checkin_weight_create` 在索引里被拉开距离的唯一机会。
4. **用比目标模型更强的模型生成。** 实测中存在「自己写的索引自己用」的同源优势，换更强模型更安全。

## 4. 批量生成策略

一次生成太多会被截断，导致部分工具没有卡片。**按 20~30 个一批拆分**：

```bash
# 拆成 4 批，分别生成，最后合并
python3 scripts/gen_tool_cards.py split --tools tools.json --parts 4
# 对每个 enrich_prompt_part{i}.txt 跑一次模型，产出 tool_cards_part{i}.json
python3 scripts/gen_tool_cards.py merge --out tool_cards.json
```

**验收**：

```bash
# 卡片数必须等于工具数，缺一个都会变成召回漏洞
python3 -c "
import json
cards = json.load(open('tool_cards.json'))
print('卡片数', len(cards))
bad = [k for k,v in cards.items() if len(v.get('queries',[])) < 5]
print('话术不足 5 条的:', bad)
"
```

## 5. 怎么写进检索索引

把三部分拼成一段文本，作为该工具的索引文档：

```python
def tool_index_text(tool, card):
    return " ".join([
        tool.name.replace("_", " "),      # 工具名，强关键词信号
        tool.ns,                          # 命名空间
        card.get("zh", ""),               # 语义说明
        " ".join(card.get("queries", [])),# 用户话术，权重最高
    ])
```

如果检索器支持字段权重（BM25F / Elasticsearch 的 boost），建议：

| 字段 | 权重 |
|---|---|
| queries | 3 |
| zh | 2 |
| name | 2 |
| 原始描述 | 1 |

## 6. 维护

**什么时候要重新生成**：
- 新增工具时（必须，否则新工具检索不到）
- 工具改名或改语义时
- 用户实际 query 与现有话术分布差异大时（从 `agent_traces` 或日志里采样对比）

**什么时候不用重生成**：调整 K、换检索后端、加向量通道。这些都只改检索层，不碰索引文本。

**建议加一个回归检查**：从真实调用日志里抽 100 条「用户 query + 实际调用的工具」，跑 recall@10。低于 95% 就说明卡片需要更新。这比人工 review 卡片有效得多。
