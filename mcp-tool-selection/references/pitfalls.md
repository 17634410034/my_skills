# 方法论踩坑：做这类实验时的九个陷阱

这些坑是 2026-10 那次实验里真实踩过或差点踩到的。**它们与 MCP 无关，任何「验证某方案是否有效」的实验都会遇到。**

---

## 坑 1：只看百分比，不看配对表

**症状**：A 方案 23/24，B 方案 22/24，于是得出结论「A 比 B 好 4.2 个百分点」。

**为什么错**：24 条里可能有 23 条两个方案答案一字不差，只有 1 条有分歧。这时「4.2pp」的全部信息量就是那 1 个样本。

**怎么做**：永远算配对四格表 + McNemar。

```
            B 对    B 错
A 对         a       b
A 错         c       d
```

只有 `b` 和 `c` 携带信息。`b+c=1` 时 p=1.0，无论百分比看起来差多少。

```python
import math
def mcnemar(b, c):
    k = min(b, c)
    return min(1.0, 2*sum(math.comb(b+c, j) for j in range(k+1)) / 2**(b+c)) if b+c else 1.0
```

**本次教训**：96% vs 92% 看起来是 4pp，实际 p=1.0，只能说「不劣于」。

## 坑 2：不切 dev / hold-out

**症状**：在全部样本上调参，然后报告同一批样本的结果。

**为什么错**：任何参数选择都会往样本上拟合。调到 K=10 恰好覆盖全部样本，就分不清「K=10 真的好」还是「K=10 恰好适合这批任务」。

**怎么做**：先切 40% 出来当 hold-out，**只用来验收，全程不看**。调参改到 hold-out 上见效时，说明你已经在偷看了。

本次做法：75 条切成 dev 30 / hold-out 45。所有盲测（n=24）都取自 hold-out，与调参集零重叠。

---

## 坑 3：干扰池只造跨域项，测不出真难度

**症状**：为了测「工具多会不会让模型变笨」，塞入大量支付、邮件、日历、k8s 工具。

**为什么错**：这些工具和测试任务**语义毫无重叠**，模型一眼就排除。实测 1000 个里有 900 多个这种干扰，准确率和 200 个时**完全一样**；错误全部落在核心工具内部，没有一条被跨域干扰带偏。

**真正的难度来源是「同域近义」**：同一业务对象上的多个动作变体。`body_get_weight` / `body_get_waist` / `body_get_hip` 挤在一起，才是模型会翻车的场景。

**怎么做**：干扰池按「命名空间 + 业务对象 × 动作」生成，密度要贴近真实系统。判断标准：如果人扫一眼就能排除某个干扰项，它就构不成难度。

---

## 坑 4：生成索引文本时喂了评测任务

**症状**：为了让检索效果好，把「用户可能怎么问」直接按评测集里的句子写。

**为什么错**：数据泄漏。召回率会虚高，上线后崩。而且你永远不会发现，因为这个数字看起来「很好」。

**怎么做**：生成工具卡时只喂工具的 name / namespace / 原始描述 / 参数。**物理隔离**：生成脚本和任务集不放在同一目录，提示词里不引用任何任务文件。

本次做法：生成提示词写到 `/tmp/mcp_eval/enrich_prompt_part*.txt`，由独立子进程只读该文件，明令禁止读 `taskset.py`。

---

## 坑 5：盲测不防对答案

**症状**：让模型做题，任务 id 是 `t001`、`t002`，提示词和评测脚本在同一目录。

**为什么错**：模型（或跑模型的 agent）可能读到答案文件；即使不主动读，id 顺序也可能暴露难度分组。

**怎么做**：
- 任务 id 全部替换成随机串，映射表单独存
- 提示词写到工作区之外的临时目录
- 明确告诉执行者「只允许读这一个文件，禁止读 .py 或其他 prompt_*.txt」
- 每条任务只给「用户原话 + 候选清单」，不给难度标签

---

## 坑 6：用流式接口测 TTFT 但网关缓冲了

**症状**：测出「10 个工具也要 11 秒」「TTFT ≈ 总耗时」。

**为什么错**：流式响应被网关整体缓冲后一次性返回，你测到的不是首 token 时间，是完整往返时间。这样测出来的延迟曲线没有任何意义。

**怎么诊断**：发一个极短 prompt（十几 token 输入、几个 token 输出），如果 TTFT 仍然接近总耗时，就是被缓冲了。

**怎么办**：换直连端点，或改用非流式但足够小的 `max_tokens`。也可以先测「空 prompt 的固定开销」，把网关开销从数据里减掉。

---

## 坑 7：没关思考模式就测延迟

**症状**：测出各种离谱数字，`max_tokens: 16` 也不管用，输出很长。

**为什么错**：qwen3.x 等模型默认开启思考模式，会先吐几百个 reasoning token，`max_tokens` 压不住思考部分。测出来的「TTFT」里全是思考耗时。

**怎么做**：显式关闭。

```python
# OpenAI 兼容接口，qwen 系
body["chat_template_kwargs"] = {"enable_thinking": False}
```

其他厂商各有开关（`thinking: {type: "disabled"}`、`reasoning_effort: "none"` 等）。**测 prefill 之前先确认输出里没有 reasoning 内容。**

---

## 坑 8：被代理劫持导致的「假故障」

**症状**：所有本地端口都返回 502，包括自己都没启动的端口。

**为什么错**：`HTTP_PROXY` / `HTTPS_PROXY` 环境变量把所有请求（包括 `127.0.0.1`）都劫到了代理。代理连不上目标，统一返回 502。

**怎么诊断**：

```bash
env | grep -i proxy
curl --noproxy '*' -s -m 4 -o /dev/null -w "%{http_code}\n" http://<your-endpoint>/v1/models
```

如果 `--noproxy` 后从 502 变成 401 或 200，就是这个原因。

**怎么做**：Python 里显式绕过：

```python
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
```

或 `export NO_PROXY='*'`。**这会浪费大量时间，建议作为任何网络类实验的第一步检查。**

---

## 坑 9：批处理任务，摊薄了成本差异

**症状**：为了省调用次数，把 12 条任务塞进一个 prompt，每条共用同一份工具清单。

**为什么错**：真实调用是「一条任务一个请求」，全量方案每条都要重发全部 schema。批处理后，12 条任务只付一次清单成本，**严重低估全量方案的真实成本**，让对比失真。反过来，检索方案每条任务有独立的候选清单，prompt 反而比全量臂长，吃暗亏。

**怎么做**：成本类结论（token、延迟）必须按**单条任务单次调用**计算，不要用批处理数字。准确率可以用批处理，但要注明这个混杂。

## 附：一条元教训

**先做诊断，再做优化。**

本次最大的转折点是：v1 里检索输给全量，我最初归因为「检索器不够好」，准备去换向量检索、调融合权重。实际写了 `diag.py` 逐条归因 8 条漏召后才发现——**是 20 个工具的描述是空转文本，跟检索算法毫无关系**。

如果直接开始调算法，会花几天时间在错误的地方。

**诊断脚本应该先于优化脚本存在。** 具体做法：把失败样本逐条打印出来，标注失败发生在哪个环节（没召回 / 召回了但排太低 / 排对了但模型选错），统计各环节占比，再决定优化什么。
