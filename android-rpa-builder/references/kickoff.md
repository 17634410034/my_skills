# Phase 0 · 立项、可行性判定与参数确认

> 目标：在写第一行代码前，把「这件事能不能做」「按什么参数做」定死。
> 依据：`blueprint.md` 第 8 章（立项决策清单）、第 5 章（适配授权门禁）、第 6.2 节（必须自己写的部分）。

---

## 0.1 需求卡（把用户的话翻译成可执行参数）

用户通常只会说「帮我做个能自动在某某 App 上干活的 RPA」。逐项补齐下表；每项给出默认值，
不要为了凑齐而反复打断用户（见 0.4）。

| # | 字段 | 为什么必须问清 | 默认值（推荐） | 不填的后果 |
|---|---|---|---|---|
| 1 | 目标 App 包名 + 版本 + 安装来源 | 无障碍白名单第一项；ID 登记表要标注版本 | 无默认，必须问 | 适配全部作废 |
| 2 | 任务清单（逐条：入口页 → 动作序列 → 成功判定 → 是否需人工授权 → 最大耗时） | 决定 `TaskType` 数量、超时预算、是否需要转人工 | 无默认，必须问 | 无法评估工作量 |
| 3 | 触发方式：定时 / 后端下发 / 人工 curl | 决定要不要 cron、要不要轮询器、要不要后端契约 | 人工 curl（最小可用） | 多写一套调度 |
| 4 | 无人值守时长与时段 | 决定屏幕保活、电池白名单、前台服务类型（见 pitfalls 的 Android 15 限制） | 7×24 | 半夜被系统杀掉 |
| 5 | 是否已有业务后端（鉴权方式 / 上传方式 / base url 注入） | 决定 `Endpoints` 契约与 SDK 超时矩阵 | 无后端（先只做设备侧） | 契约返工 |
| 6 | 控制面形态：单机直连 / 网关多机 | 决定要不要写网关与设备注册表 | 单机直连（LAN 或 adb forward） | 多余架构 |
| 7 | 设备型号 / ROM / Android 版本 | 厂商私有开关与 appops 码强相关 | 无默认，必须问 | 权限引导白做 |
| 8 | 端口：`DEVICE_PORT` | 固定写进 BuildConfig，不动态分配 | 9527（host 端口派生 19527） | 多设备混淆 |
| 9 | 设备令牌如何下发与轮换 | 设备 HTTP 写操作必须鉴权（第 7.1 项） | 配置下发 + 回环兜底 | 同网段任何人可驱动手机 |
| 10 | 仓库落点：新建目录 / 并入既有仓库；是否允许建分支与提交 | 脚手架会写文件，不碰 git | 新建空目录；**不建分支、不提交** | 污染用户工作区 |
| 11 | 是否涉及向真人发消息 / 资金 / 隐私数据 | 决定授权门禁强度与合规风险 | 涉及即逐动作授权 | 事故与封号 |
| 12 | 目标机型是否允许旁加载 APK（非商店分发） | 决定 targetSdk / FGS 类型策略 | 允许（内部托管机） | 上架合规返工 |

## 0.2 可行性三问（必须真机证据，不许凭经验）

三条全部通过才进入 Phase 1。任一条不通过 → 输出「不可行 / 需替代方案 / 需要额外技术手段」
并停止，**不要先写代码再发现问题**。

### 问 1：目标页面的控件树可读吗？

- 动作：装好脚手架、开启无障碍后，逐页执行 `tools/capture-context.sh`（Phase 3），检查 `ids.txt` 与 `dump-ui.txt`。
- 通过标准：关键页面能读到**稳定 `resource-id`**，或至少有稳定 `text`/`contentDescription`。
- 不通过的典型形态：WebView 内容为空、自绘 Canvas、游戏引擎渲染、`resource-id` 每次随机。
- 处理：换用文本/描述定位；仍不行则判定「需要逻辑修改或不可行」，写成停止线。
- 依据：第 5 章停止条件（节点无稳定 ID ⇒ 不许猜）、第 3.7 节（ID 登记表）。

### 问 2：动作能用「点击/长按/输入/滚动/返回/截图」表达吗？

- 逐条任务地问：这条任务全程只需要上述原语吗？
- 高风险形态（必须单独列风险，不要沉默吞掉）：
  - 图形/滑块验证码、需要人脸的活体校验
  - 系统级授权弹窗（支付、定位、录屏）——无障碍点不到或点错代价大
  - 目标 App 检测到无障碍/调试而拒绝服务
  - 需要拖拽排序、双指手势、多点触控的真实业务
- 处理：把每条风险写进任务清单的「已知限制」，并明确「失败时转人工」。
- 依据：第 2.3 节动作原语清单、第 3.1 节点击降级阶梯。

### 问 3：合规与风控怎么过？

- 目标 App 服务条款是否禁止自动化？账号是自有还是他人？
- 是否有「发给真人」的不可回滚动作（发消息、点赞、提交表单、下单）？
- 是否有资金、隐私、医疗等敏感数据经手？
- 处理：**真实动作逐项获得用户授权**；未授权时只采集到该动作前一页（第 5 章授权门禁）。
- 依据：第 4.2 节铁律（UI 动作不可回滚）、第 5 章授权门禁。

## 0.3 立项决策清单（16 项，逐条填写；空白视为未决策）

来自 `blueprint.md` 第 8 章，逐条给默认值。把填写结果写进项目 README 的「立项决策」一节。

| # | 决策 | 默认/建议 |
|---|---|---|
| 1 | 目标 App 包名 + 窗口包名白名单（目标、`android`、系统分享、systemui、厂商安全中心） | 脚手架已内置模板，补目标包名即可 |
| 2 | `<DEVICE_PORT>` / `<HOST_PORT>` / 是否需要 `<GW_PORT>` | 9527 / 19527 / 不需要 |
| 3 | 运行期是否依赖 USB？ | 否（执行链必须免线，ADB 只做运维） |
| 4 | 设备 HTTP 是否鉴权？令牌如何下发与轮换 | 必须鉴权；配置下发；空令牌仅回环 |
| 5 | `TaskType` 列表 + 每个动作的超时预算与最大耗时 | 逐条任务填；超时逐层放大 |
| 6 | ID 登记表分区方式与负责人；证据包存放目录 | 按页面分区；evidence 目录不进仓库 |
| 7 | 日志：级别、字段、脱敏白名单、轮转、取回路径 | 已内置（写入时脱敏 + 4K 截断 + 轮转） |
| 8 | 权限引导覆盖哪些 ROM；appops 码与校验次数 | 至少覆盖目标机 ROM；MIUI 双重 set+双 get |
| 9 | 独占锁 owner 命名规范；忙时策略 | `task:<id>:<type>` / `poller:<name>`；轮询跳过、任务等待 |
| 10 | 幂等规则：哪些动作「结果未知」绝不重试 | 发送类、上报类：结果未知绝不重推 |
| 11 | 总闸语义：拒绝哪些端点、清哪些队列、保留哪些状态 | 写端点 409；清待执行队列；保留业务现场 |
| 12 | 持久化选型与重启恢复策略 | 结果落盘 + 阶段标记断点续跑 |
| 13 | 后端契约：鉴权、base url 注入、超时重试矩阵 | 表驱动；`Authorization` 头 + TLS |
| 14 | 设备注册表由谁维护（serial ↔ IP ↔ 名称 ↔ 目标 App） | 外置文件/DB，禁止硬编码 |
| 15 | 取证脚本与防回归 guard 接入位置（人工 / CI） | 至少人工；CI 更佳 |
| 16 | 文档真源清单（哪份 API 文档由代码生成） | 端点表从代码生成，避免漂移 |

## 0.4 一次问完，不要多轮打断

把「最关键的 2–4 个形态决策」塞进**一次** AskUserQuestion，每问 2–4 个选项、**第一个选项标「推荐」**：

- Q1：是否需要业务后端与网关（影响架构量级）
- Q2：触发方式（人工 / 定时 / 后端下发）
- Q3：项目落点（新建目录的绝对路径）
- Q4：无人值守时长与目标 ROM（影响前台服务类型决策）

信息不足但可推导的（端口、包名命名风格、日志级别）**写成假设继续走**，不要问。假设记进
项目 README 的「假设账本」，格式：

```
A1 · 目标 App = <包名>            依据：需求原文「就是那个 App」+ 用户口述
A2 · 触发方式 = 后端下发          依据：需求提到「服务端会派单」
A3 · 无人值守 = 7×24              依据：需求提到「一直挂着」
```

每条假设写清「若不成立的影响」——A1 错了整份适配作废。

## 0.5 权限边界（动手前必须明确的四条）

1. **只在用户指定的目录写文件**；不要 `git init`、不要建分支、不要提交，除非用户明确要求。
2. **永不卸载、永不清数据**：只覆盖安装（卸载会丢无障碍授权与设备身份，等于重置线上环境）。
3. 目标 App 的真实动作（发送、保存、删除、清空、支付）**逐项授权**。
4. 密钥、令牌、日志、控件树、截图**不进仓库、不外发**；外发前先脱敏。

## 0.6 停止线

出现以下任一情况，停止并向用户报告，不要硬做：

- 关键页面无稳定 ID / 文本 / 描述；
- 任务必须依赖验证码、人脸、系统级授权弹窗等无障碍做不到的环节；
- 用户未授权真实动作，但任务要求执行该动作；
- 目标 ROM 无法开启所需后台权限（自启动 / 后台弹出界面），且无人值守必要性很高；
- 需求要求修改目标 App 或使用 root / instrumentation 等超出无障碍范围的手段（需重新立项）。
