## 〇、交付物定义（读懂这一节，其余都是实现细节）

**最终交付的不是「做完了的东西」，而是「一份别人能照着做完的说明书」。**

这决定了三件事：

1. **读者变了。** 从「有上下文的 Agent1 自己」变成「一个没参与过任何讨论、不知道你项目历史、也没听过你口头解释的新 agent」。它唯一拥有的就是这份文档加代码仓库。
2. **标准变了。** 自己用的文档允许「参照现有实现」「按项目惯例」这类省略——接手方不知道什么是惯例。所有隐含知识必须显式化。
3. **验收变了。** 文档好不好，不能靠读着顺不顺判断，要靠在**冷读试跑**中，一个陌生 agent 能不能不提问、不猜、直接执行成功。

一句话：**这份文档的验收测试，是另一个 agent 的执行过程。**

## 一、角色定义与模型配置

| # | 角色 | 模型（默认：阿里百炼 Token Plan） | 职责 | 边界 |
|---|---|---|---|---|
| **Agent1** | 作者 | **默认由主持担任**（API 起草时 qwen3.8-max，族 qwen） | 项目分析（先落 `recon.md` 行号级事实底稿）、写开发文档、按评审意见修复、按冷读缺口补齐 | 只写不改判；不参与给自己打分。主持撰写/修复时标 `AUTHORED-BY-HOST`/`FIXED-BY-HOST` 并在交付声明（v2.5：单次 API 生成整份长文档必超读超时，故默认路径就是主持写） |
| **Agent2** | 可行性审稿人 | **glm-5.3**（族 zhipu） | 审「别人能不能照着落地」+ 信息完备性审计 | 不看 Agent3 意见，独立出单 |
| **Agent3** | 正确性审稿人 | **deepseek-v4-pro**（族 deepseek） | 审「照着做出来会不会错」 | 不看 Agent2 意见，独立出单 |
| **Agent4** | 合并去重 | **qwen3.8-flash**（族 qwen） | 两份清单机械归并、去重、编号、建溯源表 | **不做分级裁定、不做技术判断** |
| **冷读试跑者** | 陌生验证者 | **glm-5.2**（族 zhipu） | 阶段 7：只拿文档，报缺口、试跑 1–2 张卡 | **未参与任何评审**；不许问作者 |
| **冷读执行者** | 陌生执行者 | **qwen3.8-max**（族 qwen） | 阶段 9：按 v1.0 文档实施 | **必须全新会话**，只拿文档 |
| **主持** | 仲裁 | 我 | 分歧裁定、轮次控制、文档版本管理 | 僵局交人，不自行放行 P0 |

### 1.1 异质性约束（比模型强弱更重要）

这三条是硬约束，破了流程就失去意义：

1. **Agent2 与 Agent3 必须异族于 Agent1**。同一模型族共享训练数据与偏好，盲区重合，双审退化成一个审。
   **注意「族」不是「通道」**：阿里百炼 Token Plan 一个通道里同时提供 Qwen / GLM / DeepSeek 三家模型，`provider` 字段完全相同，但族不同、盲区不重合，异质性依然成立。反之，同一通道里换成两个 qwen 模型则是无效双审。
2. **冷读试跑者必须未参与过任何评审**。Agent2/GLM、Agent3/DS 在阶段 2 和 6 已反复读过文档，被污染了，不能再当陌生者用——那是假装陌生。
3. **冷读试跑者与 Agent1 必须异族**（见下）。同族同模型换会话只解决了「记忆污染」，没解决「盲区重合」。

**单通道代价**：三家模型挤在一个通道上，通道故障会导致双审同时失败。介意就给 Agent1 配 fallback，或把某个审稿人指向官方 API。

### 1.2 通道能力边界（v2.5 新增，直接决定哪些话不能让审稿人说）

用 `hdr.py` / `hdr_ask` 这类 HTTP API 调用时，Agent2/Agent3/冷读者**只有对话能力，没有文件读写与命令执行能力**。三件事必须照办：

1. **「§0.1 每条假设到仓库核实」这条指令对 API 审稿人做不到**——它们只能判断「文档有没有给出可核对的依据」。与代码事实相关的条目，**由主持回仓库逐条核实**（带 `文件:行号`），结果单列一节写进 `resolution.md`，并在交付声明里说明「核实由主持补做」。
2. **API 审稿人的结论不是事实**。它们的「依据」栏经常是推测；推测被写进文档，就成了下一轮冷读要拆的洞。拒签与 P0 一律先回代码验事实，再决定改方案还是反驳。
3. **上下文预算要给正文留位**。`collect_context` 附带的整仓文件树已限制在剩余预算的 30%，但仍推荐把 `meta.json` 的 `repo` 设为 `null`、`context` 只放 `recon.md`——审稿人需要的是文档 + 可核对的行号证据，不是一棵大树。

要用「能读代码的审稿人」，就换成 spawn 有 Read/Grep/Bash 权限的 subagent；代价是它落回本宿主的模型族，`review_mode` 要降级为 `session` 并声明——**别让两种审稿方式混着用而不说明**。

### 1.2 冷读试跑者与冷读执行者不能配同一个模型

**两个角色目的不同，选型原则相反：**

| | 阶段 7 冷读试跑者 | 阶段 9 冷读执行者 |
|---|---|---|
| 目的 | **发现文档缺陷**（纯验证） | **把文档变成代码**（要产出） |
| 需要什么 | 异族视角、字面理解 | 模型能力、长上下文 |
| 选型 | **glm-5.2**（族 zhipu，异于 Agent1 的 qwen） | **qwen3.8-max**（同 Agent1 但全新会话） |

**两条选型原则，按优先级：**

1. **异族优先**。默认用 glm-5.2 而不是 qwen 系，因为它和作者不是同一套脑子。若追求最强异质，可换成本流程完全没用过的厂商（Kimi / Gemini / GPT）。
2. **同族时选小尺寸**。反直觉但成立：小模型不做脑补，倾向严格按字面执行，文档有歧义它就直接卡住——这正是你要的信号。大模型太聪明，会用先验把洞填平。所以哪怕走同族，也该用 flash 而不是 max。

同族同模型是唯一不可接受的选择：换会话只隔离了记忆，脑补习惯一模一样。

### 1.3 关于 Agent4 用 flash

选 flash 做合并去重合理——这是体力活，要快、要省，不需要深度推理。但有两条必须补：

- **只做机械归并，不做分级**。P0/P1/P2 的定级、共识项 / 分歧项的判定涉及语义矛盾识别，flash 容易漏判「表述不同但根因相同」，或错并「看着像其实两回事」。分级交给主持复核。
- **必须产出溯源表**。合并时保留原始条目 ID 映射，每条原始意见都能查到去向（合并进哪条 / 被谁判为重复 / 为何驳回）。否则弱模型在合并环节丢失信息，前面两个强模型的评审投入就白花了。

### 1.4 两位审稿人视角必须正交

否则等于只审了一遍：

- **Agent2 关注「可执行性」**
  - 架构是否合理、依赖是否齐全、有没有漏掉的模块、工作量是否低估
  - 是否与项目现有约定冲突、是否与现有代码风格/目录结构一致
  - **信息完备性（v2.0 新增，权重最高）**：以「我是接手的 agent」的视角，逐项列出「文档没告诉我、但我必须知道」的信息——具体文件路径、函数签名、数据结构、命令、配置项、枚举值、错误码
- **Agent3 关注「正确性与破坏面」**
  - 边界条件、异常与失败路径、并发与数据一致性、向后兼容
  - 对现有功能的影响、回滚方案、测试点是否够、验收断言是否可机器判定

### 1.5 评审强度三级与降级协议（v2.5 新增）

**背景**：平台可能不允许指定模型，或环境缺密钥。过去的写法是「若无法指定模型，至少保证两个独立会话」——这句话等于**许可静默降级**：执行者不必告知任何人，降级产物照样交付为 v1.0。这是本 SOP 第二个"免审批逃生门"（第一个是「有歧义先问清」）。

| 级别 | 条件 | 盲区 | 能否称「双审」 |
|---|---|---|---|
| `full` | 两位审稿人跨**模型族** | 基本不重合 | ✅ |
| `session` | 同族不同会话 / 同模型换会话 | 重合，仅隔离记忆 | ⚠️ 只能叫「多会话复核」 |
| `single` | 一个会话审两遍 | 完全重合 | ❌ 等于没审 |

**降级必须走三步，缺一即视为违规**：

1. **先穷尽不降级的办法**：平台 Agent 工具若支持 `model` 参数（default / lite / reasoning / 模型 id），先用它制造尺寸差；再试备用通道（官方 API 的独立 key）。**"模型不可指定"这句话要能被验证，不能是推测。**
2. **写降级记录** `.hdr-gate/<名>/degraded.md`：级别、原因（具体到缺哪个环境变量）、试过哪些办法、丢了什么。缺密钥就写 `TOKENPLAN_API_KEY 未设置`，不要写「环境不支持」。
3. **交付时第一句声明**：级别、审稿人真实模型、Agent4 是否真跑、假设核实率。低于 `full` 还要说明补什么能重跑到 `full`、代价多少次调用。

**已知后果（必须在文档 `known_blindspot` 里写出来）**：同族双审会**一起看错同一个前提**——两个会话可能都"验证"通过文档里一个根本不存在的前提，这不是异构验证，只是同一个人做了两遍。

## 二、流程（阶段 -1 与 0–8 在流程内；阶段 9 为交接后动作，不计入流程）

### 阶段 -1 · 澄清预算（歧义不阻塞判定）
- **核心命题**：**判定只依赖需求规模，不依赖需求细节。** 说不清"哪个平台"不影响判断"这件事要新建对外契约 + 鉴权、跨 3 个以上文件、影响现有链路"。
- **三条硬规则**：
  1. **澄清不是前置门禁**。永远先判定，再讨论细节。（v2.3 修正：原规则「需求有歧义 → 先问清，不进流程」会强制流程在判定前卡住，制造两轮打断）
  2. **判定前最多 1 轮、最多 4 问；判定后按问题类型放宽**（v2.5 修正）。每问必须自带默认值，形式 `问题（默认：A，理由：…）`。**判定前**那一次交互把「要不要上门禁」和「最关键的 2–3 个形态决策」合并问完；**判定后**，凡是会改变方案类型/成本量级/不可逆的设计决策（传输形态、凭据体系、工具粒度、是否允许无鉴权），允许再开 2–3 轮分层提问——这类猜错等于整篇返工，而审稿人只能质疑文档内部自洽性，兜不住方向性错误。只有「细节」和「仓库里查得到的事实」才一律转假设、不许问。
  3. **未知项写成编号假设**，存 `assumptions.md`，写进文档 §0.1，交阶段 2 审稿人打假。
- **什么值得问**（其余一律转假设）：

  | 值得阻塞 | 不值得阻塞 |
  |---|---|
  | 答案会改变**方案类型或成本量级**（包薄壳 vs 建新服务） | 参数细节（字段名、端口、超时值） |
  | 涉及**不可逆决策**（删数据、换存储引擎） | 可被后续评审推翻的实现选择（目录放哪） |
  | 只有用户知道的信息（用哪个平台、哪套凭据） | **仓库里能查到的事实**——那该去读代码 |

- **产出**：`假设账本`（A1…An，每条含依据与"若不成立的影响"）

### 阶段 0 · 门禁判定
- **输入**：用户需求（允许不完整）
- **动作**：判断是否为「复杂需求」——满足任一即启用：跨 3 个以上文件、涉及架构或数据模型决策、需引入新依赖、影响现有功能、或用户明确要求。
- **产出**：一句话需求复述 + 复杂度判定 + 影响范围 + **判定所依据的假设**
- **交互**：**判定结论 + 待确认假设 + 开工选项合并为一次交互**（一个 AskUserQuestion，≤4 问，每个都带推荐默认）。不许出现"先问澄清、等回答、再判定"的两段式。
- **不走流程的情形**：改文案、调样式、修单点 bug、加独立小函数、资料查询

### 阶段 1 · 项目分析 + 初稿
- **执行**：Agent1
- **动作**：读项目结构与关键模块 → 摸清现状、约束、可复用件、既有约定 → 输出开发文档 v0.1
- **长任务纪律**（v2.6）：本阶段是全流程最慢的一步（吞仓库上下文 + 产长文档）。
  - 上下文预算先压到 **6–12 万字符**，只给关键文件 + 文件树 + recon 结论；细节缺口交给双审与冷读逼出来
  - 必须在**同一回合内**等到落盘，不许挪到后台就结束回合（后台完成通知只在下一回合到达）
  - 全程写 `progress.log`（20s 心跳），`hdr.py status` 可判断"仍在跑 / 进程可能已死"
  - 已有 `v0.1.md` 时默认跳过，`--force` 才重跑——超时续跑不重做已完成部分
- **必须使用的骨架**：`开发文档模板-Agent可执行.md`
- **产出**：`开发文档 v0.1` + `项目分析摘要`
- **门禁**：缺「任务卡」或「验收断言」任一章节 → 打回重写，不进评审

### 阶段 2 · 背对背双审（并行，互不可见）
- **执行**：Agent2 与 Agent3 **同时**、**各自独立**评审 v0.1
- **硬纪律**：
  - 两者不通信、看不到对方意见、不共享中间结论
  - 评审依据是「文档 + 项目代码」，不是 Agent1 的口头解释
- **产出**：两份独立问题清单，每条格式：
  ```
  [编号] 位置（文档章节/代码文件） | 问题描述 | 严重级 P0/P1/P2 | 建议改法 | 依据（代码或事实）
  ```
- **分级标准**：
  - **P0 阻塞**：照此文档执行会失败、产生错误、破坏现有功能，或**接手方必须停下来提问才能继续**
  - **P1 重要**：能跑但会留坑、难维护、验收不可测
  - **P2 建议**：优化项，不阻塞

### 阶段 3 · 合并去重与分级
- **执行**：**Agent4（Qwen3.8-flash）做机械归并 → 主持做分级复核**（两段，不可合并）
- **Agent4 动作**：
  1. 两份清单按**根因**归并（表述不同但同一个坑 → 合并，标注「双审共识」）
  2. 统一编号，**保留原始条目 ID 映射**
  3. 输出候选分类（共识 / 疑似分歧），不给定级
- **主持动作**：
  1. 复核分类，纠正错并、捞回漏并
  2. 定 P0/P1/P2 分级
  3. 确认分歧项成立（一方说有问题、另一方明确说没问题）
- **产出**：`合并问题清单` + **`溯源表`**
  ```
  原始条目 → 合并后编号 → 处理结果（合并/独立/驳回 + 理由）
  GLM-01 → P0-01 → 合并（与 DS-03 同根因）
  DS-07 → 独立 → 保留为分歧项
  ```
- **说明**：溯源表是防止弱模型归并时丢信息的唯一手段。双审共识的问题可信度最高，优先修。

### 阶段 4 · 一次性修复
- **执行**：Agent1
- **动作**：拿合并后的**完整清单一次改到 v0.2**，不分两轮改、不边审边改
- **要求**：逐条回应 `[编号] 已改（改在哪一节）/ 不改（理由）/ 部分采纳（差异说明）`
- **禁止**：静默忽略；只改措辞不改方案
- **产出**：`开发文档 v0.2` + `修订对照表`

### 阶段 5 · 分歧裁定
- **执行**：仲裁主持，三方各自陈述理由
- **只处理分歧项**（共识项已在阶段 4 关闭）
- **裁定原则**：
  1. 能用代码、文档、实验验证的 → 听事实
  2. 无法验证的 → 听**保守**一方
  3. 成本权衡类 → 听作者，但必须写进「已评估的替代方案」
  4. P0 级分歧仍谈不拢 → **交用户裁决**，不自行放行
- **产出**：`裁定记录`

### 阶段 6 · 复审双签
- **执行**：Agent2 与 Agent3 各自独立复审 v0.2（并行，此轮可见裁定记录）
- **放行条件（全部满足）**：
  - 所有 **P0 已关闭**
  - 所有 **P1 有明确处置**（已修 / 转待办并写入「已知限制」）
  - P2 已登记
  - 双方各自签署：**「可交接」/「不可交接 + 阻塞理由」**
- **分支**：任一否决 → 回阶段 4（**返工上限 2 轮**；第 3 轮强制人工裁决）
- **产出**：`开发文档 v0.3`（**双签通过版**）——这是阶段 7 的输入，此前不存在 v0.3

### 阶段 7 · 冷读试跑（本流程最关键的一步）
- **执行**：**冷读试跑者 = Qwen3.8-flash（首选）**，或未参与本流程的跨厂模型（Kimi / Gemini / GPT 任一）
- **三条硬条件**（缺一条就不是冷读）：
  1. **全新会话**，无本对话任何上下文
  2. **未参与阶段 2 / 6 的任何评审**（Agent2/GLM、Agent3/DS 已被污染，禁用）
  3. **异质于 Agent1**——不同尺寸或不同厂商。同厂同型号换会话只解决记忆污染，不解决盲区重合
- **输入**：只有 `开发文档 v0.3` 加代码仓库访问权。**不给任何口头补充、不给项目背景、不给前几轮评审记录**
- **动作**（三步，逐步加码）：
  1. **复述**：用自己的话说出它理解的任务目标与改动范围 → 与文档原意比对，判断理解是否一致
  2. **报缺口**：列出「我要动手但文档没告诉我」的全部信息 → 每条都是文档漏洞
  3. **试跑**：实际执行任务卡中的第 1–2 个任务，或全部任务（视成本）
- **产出**：`冷读缺口清单`
  - 每条格式：`[缺口编号] 卡在哪个任务 | 我需要什么信息 | 文档当前怎么写的 | 我的猜测与风险`
  - **判定线**：
    - 属「路径 / 命令 / 数据结构 / 接口契约 / 配置项 / 枚举值 / 错误码」类缺口 **> 0 条 → 判定不合格**，按下表分流
    - 属「设计偏好」类缺口 → 可接受，但要求文档补一句「此处自行决策，无需询问」

  | 缺口性质 | 回流路径 |
  |---|---|
  | 信息没写全（方案本身没问题，只是没说清） | → 阶段 8 补齐 |
  | 暴露方案缺陷（照文档做会错、缺依赖、改不动） | → 回阶段 4 改方案，之后重走阶段 6 双签 + 阶段 7 试跑 |

- **本质**：这是最诚实的验收。作者和审稿人都会脑补，陌生人不会。

### 阶段 8 · 补齐定稿
- **执行**：Agent1
- **门禁（关键）**：**补齐只允许「增加信息」，不允许「改变方案」**。若补齐过程中发现必须改方案 → 立即停止，回阶段 4。理由：改方案等于让未经双签的内容混进定稿。
- **动作**：按冷读缺口逐条补齐 → 文档 v1.0（**handoff-ready**）
- **补齐原则**：
  - 缺口信息能内嵌就内嵌（直接写进文档），不能内嵌才给路径引用
  - 凡是「接手方一定会问」的问题，答案前置写进文档，而不是等它来问
- **产出**：`开发文档 v1.0` + `交接说明`（见下）
- **交付前必问（v2.5 ⑩，首次在本项目使用本 skill 不许跳过）**：
  - Q1 最终文档落哪：先归纳该项目既有开发文档的目录与命名规则，把推导出的完整路径作推荐项；
  - Q2 中间产物要不要清理：只留最终文档 / 保留全套 / 保留 recon+双审清单。
  - 选「清理」→ 顺序固定为 **移动 → 校验 → 删除 → 改写自引用 → grep 自检为空**。
- **交接说明必须包含**：
  - 文档版本、日期、基于的 commit / 分支
  - 一句话变更摘要
  - 执行前置检查清单（环境、依赖、分支状态、需先跑的迁移）
  - 执行顺序约束（哪些任务必须先做）
  - 出问题时该找谁 / 什么情况必须停下来问人

### 阶段 9 · 交付与实施（流程外）

文档 v1.0 交付后，执行者有二选一。**默认选陌生执行者（冷读执行者），Agent1 退到复核位。**

| 执行者 | 什么时候选 | 代价 |
|---|---|---|
| **陌生执行者（Qwen3.8-max，新会话）——推荐默认** | 想验证文档质量、想沉淀可复用资产、任务以后还会重复出现 | 慢、会卡、要多轮补文档 |
| **Agent1（原会话，仅限特定场景）** | 一次性任务、交付时间紧、文档不打算复用 | 文档缺陷被作者脑补掩盖，无法证伪 |

**为什么默认不用 Agent1：**

作者执行 = **出题人自己答自己的题**。文档里没写的，Agent1 脑子里有，它实施时会自动补全，而且补得对——于是文档的漏洞永远暴露不出来，阶段 7 冷读试跑的全部投入被最后一步抵消。这份文档也就永远不能被证明「可交接」，下次同类任务还得重来。

**陌生执行者的补偿机制**（解决它慢、它会卡的问题）：

1. 卡住时**只报不猜**——每处卡点都是一条文档缺陷，回流给 Agent1 补文档
2. 风格一致性靠文档 §2.2「既有约定」章节保证，不靠执行者的品味
3. 执行完成后由 **Agent1 做 code review**（它有上下文，能识别「实现偏离原意」），质量最终仍由作者兜底
4. 实施记录 + 偏离说明必须回写文档，形成 v1.1

**演进路径**：冷读执行是一次性校准，不是长期税。首轮校准完成后，项目级的「约定 + 模板 + 文件地图」已沉淀，同类任务可改由 Agent1 执行（作者盲区风险被厚文档摊薄）；但**跨领域的新任务仍必须走陌生执行者**。

若最终仍由 Agent1 实施，则视作新的执行阶段，**以 v1.0 文档为唯一依据**，实施中发现文档错误 → 立即暂停 → 回阶段 1 修订 → 走一轮快速双审。

## 三、什么叫「可执行」——6 条硬指标

文档不满足任何一条，就不算合格交付物。这是"完善"的操作性定义。

| # | 指标 | 不合格的样子 | 合格的样子 |
|---|---|---|---|
| 1 | **零上下文可执行** | 「参照现有实现」「按项目惯例」「如上所述」 | 直接给出文件路径、函数名、完整代码或字段级说明 |
| 2 | **任务卡化** | 「实现登录模块」一段散文 | 拆成 T1…Tn，每张卡有：目标 / 涉及文件 / 具体改动 / 前置依赖 / 验收断言 / 失败回退 |
| 3 | **验收可机器判定** | 「功能正常可用」 | `curl -X POST ... → 期望 200 且 body.token 非空`；`pytest tests/test_login.py -k invalid_password → 期望 1 passed` |
| 4 | **边界明确** | 不提不能改什么 | 单列「禁止区」+「必须停下来问人的条件」 |
| 5 | **版本锚定** | 无基线信息 | 写明基于 `main@a1b2c3d`、依赖版本、Node/Python 版本 |
| 6 | **非目标清单** | 只说要做什么 | 明确「本次不做」的事，防止接手方自由发挥 |

## 四、终止与升级规则

| 情形 | 处理 |
|---|---|
| P0 清零 + P1 有处置 + 双签 + 冷读无硬缺口 | 定稿 v1.0 交付 |
| 返工达 2 轮仍有 P0 分歧 | 停止内循环，列分歧点交人工裁决 |
| 冷读连续两轮仍报同类硬缺口 | 判定文档结构性问题（不是补字能解决），回阶段 1 重写对应章节 |
| 审稿人两轮提同一问题、作者明确不改 | 视为「已评估并接受」，记入已知限制，需理由充分 |
| 需求中途变更 | 流程重启，v0.x 作废，回阶段 1 |

## 五、成本参考

| 配置 | 模型调用 | 明细 | 适用 |
|---|---|---|---|
| **最小**（一次通过） | **9 次** | Agent1 写稿 1 + 双审 2 + Agent4 归并 1 + Agent1 修复 1 + 复审 2 + 冷读试跑 1 + Agent1 补齐 1 | 中等复杂，无重大分歧 |
| **典型**（1 轮返工） | **13 次** | 最小 + 返工（Agent1 修 1 + 双审 2 + 冷读 1） | 常规复杂需求 |
| **上限**（2 轮返工 + 人工裁决） | **≈17 次** | 典型 + 再一轮返工（4）+ 裁决开销 | 跨模块重构 |

注：主持（分级复核、分歧裁定、版本管理）由主控模型承担，不计入上述调用次数；阶段 9 执行成本不在本流程内。

相比之下，**文档带病交付导致的接手方返工，成本远高于这 10 次调用**——这是这套流程唯一的经济逻辑。

## 六、为什么并行优于串行（沿革记录）

串行（v1.0）的问题：Agent3 拿到的已是「按 Agent2 意见改过」的版本，会被 Agent2 的结论**锚定**，倾向只找 Agent2 没说过的问题，两个审稿人实际覆盖同一片区域。

并行（v1.1+）拿到三份独立判断（作者 + 两个互不知情的审稿人），异构模型的盲区不重合，这正是「异构冗余防共模故障」的价值。代价是阶段 2 同时跑两个模型，但省掉一轮中间修复，总轮次更少。
