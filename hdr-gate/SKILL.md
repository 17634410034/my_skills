# 异构双审门禁（HDR Gate）

产出一份**可交给陌生 agent 独立执行的开发文档**，而不是自己把代码写完。

核心逻辑：文档的验收测试，是**另一个 agent 的执行过程**。作者和审稿人都会靠先验脑补，只有一无所知的人不会。

## 九条铁律

1. **先判定，再动手。** 不判定复杂度就直接开写，是本 skill 最常见的误用。
2. **歧义不阻塞判定。** 需求说不清"哪个平台"不等于不能判定——判定只看**需求规模**。先按显式假设判定，把假设一次性抛给用户确认，**不许先问、等回答、再判定**。
3. **双审必须背对背。** Agent2 和 Agent3 各自独立评审，不共享上下文、不看到对方结论。串行评审会被锚定，等于只审了一遍。
4. **合并去重与分级分离。** 归并是体力活（flash 做），定级是判断（主持做）。两者混在一起，弱模型会错并、漏并。**归并也必须由独立会话执行**；若主持兼任（省一次调用），必须在 `trace.md` 标 `MERGED-BY-HOST` 并在交付时声明——归并丢的是「漏并」，而漏并只有另一个视角才捞得回来。
5. **冷读者不许问，作者不许答。** 试跑期间一旦口头补答，补的是对话不是文档，这次试跑就废了。它记下的清单才是要改的东西。
6. **交付文档即终止。** 本 skill 结束时**不动一行代码**。实施由用户手动开新会话完成。
7. **长任务不许脱手。** 慢阶段（draft/review/coldread）必须可观测、可续跑、**在同一回合内等到落盘**。把进程挪到后台然后结束回合，等于让任务无人看管地死在半路。
8. **落点与产物处置要问，不许默认替用户决定。** 每个项目的开发文档归属目录不一样（仓库根 / `docs/` / `openspec/specs/<日期-需求名>/`），过程产物要不要留也不一样。首次在某项目使用本 skill 时，**必须先读该目录既有文档的命名规则，再把「最终文档放哪 + 中间 .md 要不要清理」问用户**；用户说「只留最终产物」，就只留最终那一份，且删完必须把文档里指向中间产物的引用一并改掉（否则接手方照着 `degraded.md` 去开文件，开不出来）。
9. **交付路径不许空着等人问。** 用户经常提前把目标文件建好（空文件）来表示「就写这儿」。此时如果你一路闷跑到第 8 步才落盘，中间几十分钟里他看到的就是一个空文件，并且会认为你什么都没做（2026-10-26 实测：用户第 N 轮问「怎么什么都没有看到」）。**双签一通过就把 v0.3 复制/写入交付路径**，并说明「冷读补齐后只往里加信息、会再覆盖一次」；此后每完成一个阶段就刷新一遍。空占位文件不是需求，是要你早点让它长出东西。

## 第 -2 步 · 运行环境体检（三条命令，别省）

判定之前先把「这台机器到底能不能跑门禁」弄清。2026-10-26 实测三处误判都出在这里，且每一处都会把后面的流程带到错误的降级结论上。

```bash
# ① 密钥：agent 的 Bash 是非交互 shell，只读 .zshenv/.zprofile，**不会 source ~/.zshrc**。
#    用户把 TOKENPLAN_API_KEY 写在 .zshrc 里 → doctor 直接报「缺密钥」，那是误报，不是没配。
export TOKENPLAN_API_KEY="$(zsh -c 'source ~/.zshrc >/dev/null 2>&1; printf %s "$TOKENPLAN_API_KEY"')"
python3 tools/hdr.py doctor        # 每条命令都要重新注入（shell 状态不跨调用）
```

- **doctor 的「该角色无可用通道 / 异质性 ⏸ 未验证」可能是误报**：判定逻辑是「角色链上每个 provider 都要有 key」，只要 agent1 配了 `fallback` 而那个通道没 key，agent1 就被标红、异质性检查跟着显示未验证——而实际 tokenplan 一个通道里 qwen/glm/deepseek 三家都有，跨族照样成立。**别因为红字就宣布降级为 `session`。** 直接查族：`llm.heterogeneity(cfg, 'agent1', 'agent2')` 拿到 `✅ 不同模型族` 就按 `full` 走，并在 `degraded.md` 里写明「doctor 误报、按族校验通过」。
- **`--allow-missing` 只在你确认缺失的通道确实不在链上时用**，用了就要在交付话术里说明。

```bash
# ② 文档里要给出的每条「构建/生成/迁移」命令，都必须在本机实测一遍再写进 §1.2
#    （团队文档写的基准环境常常与本机不同）
docker ps -a --format '{{.Names}}' | grep -i <团队基准容器名> || echo "容器不在本机 → 必须找本地兜底路径"
which <代码生成工具> <编译器> ; <工具> --version
```

- **典型坑**：团队基准常常要求「在指定容器里跑代码生成 / 构建工具链」，而本机可能根本没起那个容器 → 照抄团队文档，写进 §1.2/§5 的验收断言从第一条就跑不通，接手方会卡在第一米并怀疑整份文档。**要么找到本机可用路径（本地工具链 + 显式 PATH 前缀 + 记录其代价），要么把「环境缺失」写成 §6.2 停止线**，绝不留着跑不通的命令交付。
- **写验收命令时，先跑一遍把真实输出抄进文档**（包括失败输出）。基线本来就红的地方要显式标注「期望：FAIL，基线既有状态」。

```bash
# ③ 暂存目录不要污染用户的 git 状态
printf '/.hdr-gate/\n' >> <仓库>/.git/info/exclude    # 本地、可逆，不改 .gitignore
```

## 第 -1 步 · 澄清预算（歧义不阻塞）

**用户交给你一个说不清的需求，是常态，不是异常。**

"我之前那个项目里的那个 agent"——这种话在你听来是歧义，在用户听来是"我已经说清楚了，你怎么这都不懂"。你要做的不是把理解成本推回去，而是**用假设承担不确定性**。

### 三条硬规则

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **澄清不是前置门禁** | 复杂度判定只依赖需求规模（改几个文件、动不动契约），不依赖细节。A 平台还是 B 平台，判定结论往往一样 |
| 2 | **判定前最多 1 轮；判定后按问题类型给预算** | 见下「两类问题，两种预算」。把「门禁许可 + 方案形态决策」塞进同一轮问完是下限做法，不是上限 |
| 3 | **每问必须自带默认值** | 没有默认值的问题 = 把决策成本转嫁给用户。格式：`问题（默认：A，理由：…）` |

### 两类问题，两种预算（易混，务必分开）

| 类型 | 处理 | 轮次预算 |
|---|---|---|
| **不阻塞判定的歧义**（细节、可被评审推翻的实现选择、仓库里查得到的事实） | 写成假设继续走，**不许先问** | 0 轮 |
| **会改变方案形态/成本量级/不可逆的设计决策**（传输形态、工具粒度、凭据体系、是否允许无鉴权） | 该问，而且**用户明确欢迎多问**——先读代码/原文，再分层问：核心机制 → 范围 → 数值粒度 → 技术形态 | 判定后 2–3 轮、每轮 ≤4 题 |

判定的那一次交互仍然只有 1 次：把「要不要上门禁」和「最关键的 2–3 个形态决策」塞进同一个 AskUserQuestion（Q1 门禁 + Q2–Q4 决策，选项第一个标推荐）。**之后**在正式动笔前可以再开第 2、3 轮。

反过来的一条硬约束：**方向性错误无法靠评审兜住**。本轮实测里，「调用方在进程内还是进程外」「端点是否必须带鉴权」这两条如果我自己拍了默认值往下写，整份文档（含双审与冷读的全部投入）会全部作废——因为审稿人只能质疑「文档内部是否自洽」，不知道用户真正要的是另一种东西。凡是「猜错就整篇返工」的决策，宁可多问一轮，别自己假设。

补记：文档里对自己替用户拍的默认值统一在正文标 `⚠`，并在末尾列「待确认清单」；用户在文档产出期间手改过原文/文档时，**以用户的版本为最新事实**覆盖原有假设，别坚持自己那版。

### 什么值得问

| 值得阻塞 | 不值得阻塞（写成假设，继续走） |
|---|---|
| 答案会改变**方案类型或成本量级**（包一层薄壳 vs 建一套新服务） | 参数细节（字段名、端口号、超时值） |
| 涉及**不可逆决策**（删数据、换存储引擎） | 可被后续评审推翻的实现选择（模块放哪个目录） |
| 只有用户知道的信息（用哪个平台、哪套凭据） | **仓库里能查到的事实**（现有接口怎么鉴权）——那该去读代码，不是问人 |

第三条最容易犯规：问用户"你们的登录接口怎么鉴权的"，答案就在代码里。**先去仓库找，找不到才问。**

### 假设账本

没确认的全部编号写下来，别只在心里记：

```
A1 · 平台 = 当前这个应用里创建的 agent    依据：需求写"这个平台"，且当前工作区只有这一处符合
A2 · 调用方 = 外部 MCP 客户端             依据：需求写"给其他 agent 调用"
A3 · 现有 agent = 提示词 + 工具配置，无独立 HTTP 入口   依据：仓库内未见部署单元
```

- 存 `.hdr-gate/<需求名>/assumptions.md`
- 写进文档 **§0.1**，标注"已确认 / 待确认"
- **假设不是免责声明，是给审稿人的靶子**：阶段 2 的 Agent2 必须专门审"这些假设是否成立"。A1 错了整份文档作废，所以每条假设都要写清依据和"若不成立的影响"

## 第 0 步 · 复杂度判定（必做，不可跳）

读完需求后，先判定是否值得上门禁，然后**把理由讲给用户听，由用户决定**。

### 判定标准（命中任一即倾向启用）

| # | 标准 | 怎么判断 |
|---|---|---|
| 1 | 跨 3 个以上文件 | 从需求描述能看出改动面 |
| 2 | 涉及架构或数据模型决策 | 要新建表/改字段/改接口契约/引入新模块 |
| 3 | 需引入新依赖 | 新库、新服务、新外部 API |
| 4 | 影响现有功能 | 有破坏面、需要向后兼容 |
| 5 | 用户明确要求 | 说了"写开发文档""出方案""给别人做" |

**不命中任何一条 → 直接告诉用户"这个不用上门禁"，然后正常做。** 不要为了用 skill 而用 skill。

### 向用户描述的话术

用这个结构，简短直接：

```
这个需求我判断【值得 / 不值得】上异构双审门禁。

命中的标准：① … ② …
影响面预估：约 N 个文件，涉及 <表/接口/模块>
走门禁的代价：约 13 次模型调用、4 个模型、预计 <时长>
不走的风险：<具体风险，比如"改错字段没人兜住，上线后才发现">

建议：<走 / 不走 / 走简化版（砍掉冷读试跑）>
```

判定后**必须让用户选，不要自行开工**。但**只有一次交互机会**，把三样东西塞进同一个 AskUserQuestion（≤4 问）：

| 问题 | 内容 |
|---|---|
| Q1 门禁 | 「我判定值得上门禁（命中①③⑤）。走完整 / 走简化版 / 直接做」 |
| Q2–Q4 关键歧义 | 每个问题 2–4 个选项，**第一个选项标「推荐」**，等于你的默认假设 |

用户全点默认 → 一次交互同时拿到判定许可和假设确认。

**需求本来就清楚（无歧义）**：只发 Q1，不要为了凑数硬造问题。

**本项目首次使用本 skill 时**，把「最终文档放哪」也塞进这一轮（Q4，默认值 = 按该项目既有开发文档目录规则推导出的完整路径），因为它是**只有用户知道、且会改变交付动作**的信息；「过程产物要不要清理」则留到交付时再问（见「交付前必问两件事」）。

**绝对不要**先发一条"我需要你确认三件事"、等用户答完再发判定——那是两轮打断，也是用户抱怨"没法直接用"的直接来源。

## 长任务协议（慢阶段怎么跑，别让任务在半路消失）

三个阶段天然慢：**draft**（吞整个仓库上下文）、**review**（两个大模型并行）、**coldread**（全文 + 仓库）。慢不是问题，**"没人知道它在跑"才是问题**。

单次调用最坏耗时 = `timeout(600s) × (retries+1)` = **30 分钟**。这 30 分钟里如果没有落地痕迹，用户问"到哪了"的时候，你已经失去控制权了。

### 六条硬规则

| # | 规则 | 具体做法 |
|---|---|---|
| 1 | **不在有 pending 任务时结束回合** | 长任务用 `run_in_background` 启动，但**必须在同一回合内阻塞等到落盘或失败**。后台完成通知只在**下一回合**到达——这一回合就结束的话，那条通知永远没人收 |
| 2 | **每阶段必须留可观测痕迹** | `progress.log`：时间戳 + 阶段 + 20s 心跳。被问"到哪了"时，答案是一行 `tail`，不是"我去看看" |
| 3 | **先算清上界再启动** | 上下文 20 万字符 × 600s 超时 = 赌一次可能要 10–30 分钟。**先切到 6–12 万字符再发**：细节缺口本来就该由双审和冷读逼出来，不必用"等半小时"换一次全量读取 |
| 4 | **算的是输出上界，不只是输入** | 非流式调用的墙钟时间 ≈ 输出 token 数 ÷ 生成速度。**draft / fix / finalize 要一次生成整份长文档（1–3 万 token），在多数网关上必超读超时**，与上下文体积无关。这三阶段默认由主持自己写（见第 1 步），审稿/归并/冷读才走 API |
| 5 | **等待要切成小于宿主单次上限的轮询** | agent 的 Bash 工具单条调用常封顶 10 分钟，且**shell 状态不跨调用**（`export` 的密钥、`cd` 的目录每条命令都要重做）。等待循环写成 `for i in $(seq 1 34); do …sleep 15…done`（≈8.5 分钟）并在同一回合内续跑下一轮，而不是等一次长命令 |
| 6 | **用「产物体积」判完成，不用「进程还在不在」** | 完成信号是文件出现且**体积比上次采样变大**（空正文的坑就在「文件生成了但是 0 字节」）：`B=$(stat -f%z 产物); for i in $(seq 1 110); do N=$(stat -f%z 产物); [ "$N" -gt "$((B+50))" ] && break; pgrep -f <进程名> >/dev/null || { echo PROC-GONE; break; }; sleep 5; done`。空/截断产物一律走 `hdr.py retry --stage … --max-tokens …` 重跑，**不要手写临时脚本调 `llm.chat`**——那会绕过 `require_artifact` 校验和 `add_cost` 记账（2026-10-26 实测踩过两处） |

### 真实反例（本 skill 用户踩过）

把 220K 字符上下文丢给 qwen3.8-max 起草，11 分钟无响应；编排者把进程挪到后台，然后**结束了回合**。用户半小时后回来发现任务"消失"，只能问"你怎么停了"。

三处都错了：上下文没切（可切到 1/3）、没有心跳（无法判断死活）、结束了回合（通知无人接收）。

**反例 2（2026-10-22，证明「压上下文」治不了 draft）**：把上下文压到 22K 字符、`max_tokens` 从 32000 降到 14000、`timeout` 升到 900s，qwen3.8-max 起草仍在 **1000s 心跳后无响应**（第一次尝试 600s 读超时）。同一个需求里 review/coldread/merge/sign 用同通道同尺寸级别的调用全部在 77–345s 内返回——差别只在**它们输出短、draft 输出是一整份文档**。结论：长文档生成不要用 API 单次调用，主持直接写。

另一条同批实测的坑：**推理模型会把 `max_tokens` 花在思维链上**。`glm-5.3` 一次评审 `out=17684`，其中 `reasoning_tokens` 占绝大多数，正文只有 3.8K；当配额给到 16000/6000 时它**返回空 `content`**，工具把 2 字节的空文件当成功落盘，下一阶段拿空清单去归并——**静默垃圾进垃圾出**。现在 `llm.chat` 见到空正文会直接报错并提示 `finish_reason` / `reasoning_tokens`，各阶段产物也有非空+格式校验。

配额的第二批实测（2026-10-26，同一 skill 的另一条真实需求）：**光提到 20000 还不够**。
- `review` 的 agent2 在 20000 下仍返回 **2 字节**（正文只有 `[P`）；提到 32000 + 压正文体量后拿到完整 14 条（541.8s，`out=27592`，其中绝大多数仍是思维链）
- `coldread` 在 20000 下返回 **0 字节**；40000 + 约束后 183.9s 完整收尾（`out=13397`）
- `sign` 在 32000 下双方都正常签出 `SIGNOFF`（74-219s）

所以 `config.toml` 的默认值是 **agent2/agent3 = 32000、agent4 = 24000、coldread = 40000**，并且 `prompts.py` 已把 `OUTPUT_TERSE_*`（条数/字数/禁止复述）硬编进审稿、签署、冷读三个角色的 system。**两件事缺一不可：提配额解决「装不下」，压体量解决「收不了尾」**——只提配额而不压正文，模型会在思维链里一直写到撞顶，照样空手而归。

### 失败与续跑

- 失败必须落 `progress.log` 最后一行写清原因，不许静默退出。
- **`draft` 检测到 `v0.1.md` 已存在时默认跳过**（`--force` 重跑），这样超时后重跑不会重做已完成的活儿。**跳过时照样跑硬门禁自检**（任务卡 / 验收断言 / 非目标），不通过直接退出——所以「主持自己写 v0.1」是被工具承认的正路，不是绕过。
- 判断死活：`tail .hdr-gate/<名>/progress.log`；最后一条超过 3 个心跳周期（60s）没有更新 → 进程大概率已死。
- 产物落点是**执行命令时的 cwd**（`.hdr-gate/` 相对路径）。`init` 会把绝对路径写进 `tools/.hdr-projects.json`，换目录执行也能找回现场，但仍应**固定 cd 到目标仓库根目录**跑全部命令，否则交付物 `<需求名>.md` 会落到别处。

## 第 1 步 · 项目分析 + 初稿

Agent1（作者）有两条合法路径，**默认选第一条**：

| 路径 | 什么时候用 | 要求 |
|---|---|---|
| **A · 主持亲自撰写** | 默认。尤其是整份文档长（>8K 字符）或通道是非流式 API | 先做仓库勘查并落一份 `recon.md`（行号级事实底稿），再按模板写 `v0.1.md`；在 `degraded.md` 标 `AUTHORED-BY-HOST` 并写清原因；交付第一句声明这一点 |
| B · API / subagent 起草 | 文档短、或宿主支持分段生成 | 上下文 ≤12 万字符；**注意输出长度才是超时主因**（见长任务协议反例 2） |

无论哪条路径，动作一样：

1. 读项目结构、关键模块、既有约定、可复用件 → **写成 `recon.md`**（每条带 `文件:行号`；未核实的单列一节「待核实」，禁止当作事实）。这份底稿同时是审稿人的靶子和主持复核时的弹药，比塞源码文件有效得多。
2. 按 `dev-doc-template.md` 骨架写 v0.1，存到 `.hdr-gate/<需求名>/v0.1.md`
3. 跑 `hdr.py draft`（已存在 v0.1 时它只做门禁自检并放行，不重复调用）

**硬门禁**：缺「任务卡（T1…Tn）」或「验收断言（可执行命令）」任一章节 → 自己打回重写，不许进评审。工具会在 draft 与跳过分支都校验，不通过直接退出。

**作者的自我约束**：主持写文档时，最容易犯的错是「把自己查到的东西当成读者也知道」——凡是要求接手方「照抄/逐字搬移」的代码，**必须内嵌进文档**，只给 `文件:行号` 等于没写（本轮冷读的头号缺口）。

## 第 2 步 · 背对背双审（并行）

用 Agent 工具**同时**起两个 subagent，**互相不传对方的存在**：

| 角色 | 模型 | 审什么 |
|---|---|---|
| Agent2 | GLM-5.3 | **能不能落地** + 信息完备性（文档没告诉我什么）+ **假设是否成立**（§0.1 逐条打假） |
| Agent3 | DeepSeek 4.1 | **做出来会不会错**（边界/异常/并发/兼容/破坏面/验收可测性） |

两个 prompt 都必须包含：
- 只给它文档路径 + 仓库路径，不给本对话任何上下文
- 明确"不得假设文档未写明的信息，凡是需要假设的地方都要列为问题"
- 明确"§0.1 的每条假设，请到仓库里验证；能证伪的直接列 P0"
- 输出格式：`[编号] 位置 | 问题 | P0/P1/P2 | 建议改法 | 依据`

产出分别存 `review-glm.md`、`review-ds.md`。

### 审稿人的能力边界（用 API 模型审稿时必须知道的限制）

当 Agent2/Agent3 是通过 HTTP API 调用（`hdr.py review` / `hdr_ask`）而不是 spawn 有工具权限的 subagent 时，它们**没有文件读权限**。于是「§0.1 每条假设请到仓库里验证」这条指令**做不到**——它们只能判断「文档有没有给出可验证的依据」。

配套要求，一条都不能省：

1. 主持必须自己回仓库逐条核实审稿人提出的、与代码事实相关的条目（路径/签名/字段/文案/行为），把结果写进 `resolution.md` 的一节（标题如「主持回仓库核实的事实」），并在 `degraded.md` 说明审稿人无文件权限。
2. **不许把审稿人的"看起来对"当事实**。它们的依据栏经常是推测；推测被写进文档，就成了下一轮冷读要拆的洞。
3. 审稿人清单为空或只有 2 字节 → **先查 `max_tokens` 是否被推理链吃满**（`progress.log` 里看 `out=` 与 `reasoning=`），不要先怀疑通道挂了或模型不可用。
4. 上下文别塞整仓文件树：`collect_context` 会把 tree 无条件插进上下文（现已限制为剩余预算的 30%，但仍应把 `meta.json` 的 `repo` 设为 `null`、`context` 只放 `recon.md`）。审稿人真正需要的是文档 + 可核对的证据行号。

### 降级协议（必须显式，不许静默）

**默认不是降级，默认是报告。** 先判定自己处在哪一级：

| 级别 | 条件 | 盲区 | 能不能叫「双审」 |
|---|---|---|---|
| `full` | 两个审稿人跨**模型族**（qwen vs glm vs deepseek） | 基本不重合 | ✅ 可以 |
| `session` | 同族不同会话，或同模型换会话 | 重合，只隔离了记忆 | ⚠️ 只能叫「多会话复核」 |
| `single` | 一个会话审两遍 | 完全重合 | ❌ 等于没审 |

**降到 session / single 时，三件事一件都不能少：**

1. **先试能不能不降。** 本平台 Agent 工具支持 `model` 参数（`default` / `lite` / `reasoning` / 具体模型 id）。至少把审稿人压到 `lite`、作者用 `default`，制造**尺寸差**——同族不同尺寸比同族同模型强一档。**别还没试就说「模型不可指定」。**
2. **写降级记录** `.hdr-gate/<名>/degraded.md`：降级到哪一级、原因、试过什么、丢了什么。原因要具体到「缺哪个环境变量」，不要写「环境不支持」。
3. **交付时第一句声明强度**，并说清「补 key 重跑要多少次调用」。

**绝对禁止**：把 `session` 级产物说成「已过双审」；frontmatter 不写 `review_mode` 就交付。

## 第 6 步 · 复审双签 → v0.3

Agent2、Agent3 各自独立复审 v0.2（此轮可见裁定记录，可只核对"自己提的 P0 是否关闭"以省成本）。

放行条件全部满足：
- 所有 P0 已关闭
- 所有 P1 有明确处置（已修 / 转待办并写入「已知限制」）
- P2 已登记
- 双方各自签「可交接」/「不可交接 + 阻塞理由」

**返工上限 2 轮**，第 3 轮强制交用户裁决。通过后产出 **v0.3**（双签通过版）。

轮次怎么数（易混，`hdr.py sign` 会在 `meta.json.sign_round` 里累计并存档 `sign-roundN.md` / `v0.3.roundN.md`）：一次「fix → sign」记 1 轮。**冷读暴露方案缺陷后回第 4 步重做，也要重跑 sign，同样计入轮次**——所以真实链路常常 3 次 sign 才收口。第 3 轮仍不过，就别再自行返工，把分歧写成一条问题交用户。

**拒签是这套流程最有价值的时刻，不是事故。** 本轮实例：DeepSeek 在 Round 2 拒绝签字，理由是「绑了五段管道插件的 role 走新端点会绕过 ⑤ 收口器」——主持回代码核实（`chat_stream` 确实不调度 `PipelineStreamRunner`）后确认它是对的，于是补了「执行前拦住 + 零 LLM 调用」的准入闸门，并在已知限制里登记「这类场景本次不对外开放」。若当时用「补一段停止线让执行者自己发现」糊过去，产出就是**不报错的错回复**。审稿人给出阻塞理由时：先回事实，事实站在它那边就改方案，站在你这边才拿证据反驳。

### 双签通过后的三个动作（顺序固定，一个都别漏）

1. **同步 frontmatter**（`hdr.py sign` 已内置：落 v0.3 时把 `doc_version` 改成 `v0.3`、`status` 改成 `handoff-ready`）。以前这里是纯复制，导致交付出去的文件正文写着 `doc_version: v0.2 / status: under-review`，而你说「双签通过」——接手方第一眼就读到一对矛盾。
2. **修掉「非阻塞知会项」**。审稿人常给这种条目：不构成否决、但你写进去会在接手方那侧卡住（实测：一处内部矛盾 + 一处文件数统计漏了 2 个测试文件，二者都「不阻塞签署」，却都会让冷读者报假缺口或让验收断言必不中）。改完在 §10 版本记录里单列一行，注明是「双签知会修补」。
3. **立刻把 v0.3 落到交付路径**（铁律 9）。不要等第 8 步——那中间可能隔 20 分钟以上，而用户手里只有一个空占位文件。

## 第 7 步 · 冷读试跑（最关键，不许省）

**找一个完全陌生的执行者**，只给 v0.3 文档 + 仓库，不给任何背景。

### 必须是「双冷读」，单路冷读会漏掉一整类缺陷（2026-10-26 实测确立）

两条纯文本类缺口（歧义、缺路径）与「文档对代码库的每一处事实断言是否成立」是**两类不同的病**，一个冷读者治不了两种：

| 冷读路 | 用什么跑 | 有无仓库读权限 | 能抓出什么 | 抓不出什么 |
|---|---|---|---|---|
| **A · 异族 API 冷读** | `hdr.py coldread`（默认 `glm-5.2`） | ❌ 纯 API 调用，只有文档正文 | 字面歧义、「我要动手但文档没告诉我」、复述偏差 | **一切需要读代码才能证伪的东西**：行号漂移、符号不存在、签名对不上、命令在本机跑不通、断言的期望输出不可能成立 |
| **B · 宿主侧只读 subagent 冷读** | Agent 工具起全新上下文的只读执行者 | ✅ 可读全仓、可跑只读命令 | **事实性错误**（这一类价值最高）、跨文件一致性、命令可否执行 | 字面脑补较少（模型偏强），对"文档没说清"的敏感度弱于 A |

**两路都要跑，产出合并后进第 8 步。** B 路的 prompt 要写死这四条：

```
你是这份开发文档的冷读执行者。只读，禁止创建/修改任何文件，禁止跑会改状态的命令。
你只能拿到两样东西：文档 <绝对路径>，和仓库 <绝对路径>。没有任何背景，也不许提问。
1. 逐张任务卡核对文档里每一处对仓库的事实断言（路径、行号、符号名、函数签名、
   字段与枚举、import、命令、断言的期望输出）。发现与仓库不符的，单列一节
   `## 事实性错误`，格式：文档的主张 | 仓库实况 | 证据 file:line。这一节比缺口清单更重要。
2. 「我要动手但文档没告诉我」的信息逐条编号列出，不许用常识补全。
3. 按文档字面顺序纸质试跑 T1→Tn，写出每张卡你会执行的步骤，以及在哪一步必须停下、为什么。
4. 不许提改进方案、不许评价设计优劣。你只负责暴露空白。
```

> 本轮实测：A 路交回 12 条缺口，其中 3 条真缺陷（用例归属错、helper 未定义、夹具未给）；
> B 路负责证伪「文档说的行号/签名/命令是否真的存在」——这正是 A 路结构上做不到的。
> 只跑 A 就交付，等于把「文档与代码是否对得上」这件事交给运气。

用 Agent 工具起一个**全新上下文**的 subagent。三条硬条件：

1. 全新会话，无本对话任何上下文
2. **未参与第 2/6 步的评审**（GLM、DS 已被污染，禁用）
3. 异族于 Agent1 —— 默认用 `glm-5.2`（zhipu 族，作者是 qwen 族）；同族时必须选小尺寸

**纯净度是这一步的全部价值**：`hdr.py coldread` 默认**不**附带项目上下文与作者的 `recon.md`（要带得显式 `--with-context`）。把作者的事实底稿喂给冷读者，等于让它带着作者的先验补课，缺口清单会假性变干净——那这份试跑就白跑了。

> 实测提示（已修复）：冷读曾被 `max_tokens` 截断到「正文止于 GAP-15 行中」甚至返回 0 字节。现在 `coldread` 配额 40000 且 system 里带体量硬约束；若仍撞顶，用 `hdr.py retry --stage coldread --max-tokens 48000`，**不要**为了「拿全 20 条」重跑整条流程。已报出的缺口足够开工——截断处的判断按「同类缺口继续按同一原则处理」即可。

> **为什么试跑要用"笨"模型**：小模型不脑补，倾向严格按字面执行。文档有歧义它会直接卡住——这正是你要的信号。max 太聪明，会用先验把洞填平。

prompt 必须包含这三条指令：
- 你是第一次接触这个项目，只有这份文档和代码仓库
- **不要问任何人**，把所有疑问写进清单
- **严格按文档字面执行**，不要用常识补全任何未写明的内容

让它做三件事：

1. **复述**：用 5 行以内说出它理解的目标与改动范围
2. **报缺口**：列出「我要动手但文档没告诉我」的全部信息
3. **试跑**：实际执行 T1–T2

产出 `cold-read.md`，每条：`[缺口编号] 卡在哪个任务 | 我需要什么信息 | 文档当前怎么写 | 我的猜测与风险`

### 判定与分流

| 缺口性质 | 判定 | 去向 |
|---|---|---|
| **事实性错误**（文档写的行号/符号/签名/命令/期望输出与仓库不符） | **最高优先级不合格** | → 第 8 步逐条改正，并在版本记录单列；这类错不会让接手方提问，只会让他**照着写完再回头查**，代价最大 |
| 路径 / 命令 / 数据结构 / 接口契约 / 配置项 / 枚举值 / 错误码 缺失 | **不合格**（>0 条即不合格） | → 第 8 步 |
| 暴露方案缺陷（照做会错、缺依赖、改不动） | 不合格 | → 回第 4 步改方案，重走第 6、7 步 |
| 设计偏好类 | 可接受 | 要求文档补一句「此处自行决策，无需询问」 |
| **「文档没给完整实现代码」类**（要函数体、要夹具数据、要你自填断言） | **多为假缺口**，但要就地处置 | 说明任务卡没声明授权边界：在每张卡补一句「本卡只给签名与规则，实现体自决，无需询问」，并把该断言所需的**夹具内容/期望输出**直接内嵌。冷读者不会去猜「不给代码是不是故意的」，你要么写清楚，要么就补内容 |

**试跑期间绝对不许口头补答**。它问"user.py 在哪"，你回了"src/models/user.py"——这句话就该写进文档，而不是说给它听。

## 第 8 步 · 补齐定稿 → v1.0 交付

Agent1 按缺口逐条补齐。

**硬门禁：只允许增加信息，不允许改变方案。** 若补齐时发现必须改方案 → 立即停止，回第 4 步。改方案绕过双签，等于让未经评审的内容混进定稿。

补齐原则：
- 能内嵌就内嵌（把代码片段、字段表、命令直接写进文档），不能内嵌才给路径
- 凡是"接手方一定会问"的问题，答案前置写进去，别等它问

**定稿前逐条自检**（本轮冷读实测出来的，一条不过就别交付）：

| # | 检查 | 为什么会踩 |
|---|---|---|
| 1 | 文档里凡是「照抄 / 逐字搬移 / 复制」的指令，被复制的对象**必须有完整代码块**，不能只有 `文件:行号` | 冷读第一轮的 GAP-01/03/04/18 全是这一类；执行者要么猜、要么卡死 |
| 2 | 每条命令能**原样执行**：不出现未定义的 shell 变量（`$(make_key)` 这类）、不写机器相关的绝对路径解释器（统一 `uv run python` / `pnpm`） | 断言不可执行 = 该卡没有验收 |
| 3 | 需要真环境（起服务、LLM 凭据、内网 DB）的卡，必须显式标 `[ENV]` 并写「环境不具备时按停止线报告，禁止伪造输出」 | 不标就会让接手方以为可自动验证，或在无环境时硬编结果 |
| 4 | 交付前查一次 `git status`：目标仓库若有**未提交的并行改动线**动了文档引用的文件，必须在 §1 写「基线告警」并要求执行者以自己检出的 tree 为准 | 行号会漂移；本轮 `test_mcp_tool_registry.py` 正在被另一条线扩充 |
| 5 | 交付物与 `.hdr-gate/` 都是**未跟踪文件**，文档 §6.1 禁止区必须写明「不得 `git add -A` 带进提交」（仓库 `.gitignore` 常常并不忽略它们） | 否则流程产物被误提交进代码库 |

## 交付物

| 产出 | 路径 | 说明 |
|---|---|---|
| **开发文档** | **交付前与用户确认**（首次在本项目用本 skill 必问）；确认不了才兜底落在工作区根目录 | **唯一交付物**，用户手动交给新会话执行 |
| 中间产物 | `.hdr-gate/<需求名>/` | v0.1–v0.3、双份清单、溯源表、冷读缺口、裁定记录。**交付时问用户要不要清理；选择清理则只留最终文档** |

`<需求名>.md` 用中文短名，如 `用户登录态改造.md`、`订单导出功能.md`。

### 交付前必问两件事（本项目首次使用本 skill 时不许跳过）

默认落点（仓库根 `<需求名>.md`）只是**兜底假设**，不是答案。同一个 skill 在不同项目里，开发文档的归属目录差别极大——本轮实测：`py-boohee` 的需求文档全在 `app/service/ailife/openspec/specs/<YYYYMMDD>-<需求名>/<需求名>-开发文档.md`，落在仓库根反而是错的。

| # | 问什么 | 怎么问（自带默认值，一轮问完） |
|---|---|---|
| Q1 | **最终文档放哪** | 先 `ls` 该项目既有开发文档目录，归纳出真实命名规则（日期前缀？编号前缀？目录名=需求名？文件名带不带「-开发文档」后缀？），把**按该规则推导出的完整路径**作为推荐默认值，另给「仓库根」和「自定义路径」两个备选 |
| Q2 | **过程产物要不要清理** | 选项 A（推荐）：只保留最终文档，删除 `.hdr-gate/<需求名>/` 全部中间产物；选项 B：保留全套（便于复核评审过程）；选项 C：只保留 `recon.md` + 两份评审清单，删掉 v0.1–v0.5 版本链 |

用户选「清理」→ **只保留最终那一份 .md**。删除前必须逐条做到：

1. **先移动、再验证、最后删**。确认最终文档已在新位置且字节数正确（`ls -la` + `wc -c`），才允许 `rm -rf .hdr-gate/<需求名>`。顺序反了就是把交付物删了。
2. **删完必须回头修文档里的自引用**。文档活着、它引用的产物死了，就是给接手方留悬空指针。逐条清理这些位置：
   - frontmatter `known_blindspot` 里「见 `.hdr-gate/.../degraded.md`」之类的路径；
   - §10 变更记录「依据」列的 `recon.md` / `merged.md` / `sign.md` / `coldread.md` —— 保留文件名作**溯源线索**，但要在表后补一句「过程产物已按用户要求清理，名称仅作溯源线索、不再可打开；需复核评审过程请重跑门禁」；
   - §1/§5/§6/§7/附录 A 里指向 `.hdr-gate/` 的**执行期记录**路径（`t0-findings.md`、`pytest-baseline.txt` 等）。这些是接手方要写的东西，不能跟着一起消失：**改指到仓库已 gitignore 的临时目录**（如 `.tmp_trace/<需求名>/`，正文里定义一次 `$REC` 后续统一引用），并在 §6.1 禁止区说明「执行期记录只写 `$REC`，交付文档所在目录应随需求提交」。
3. **修完自检**：`grep -n "hdr-gate" <最终文档>` 必须为空；`grep -c "^### T"` 与 `^## 附录` 数量不变（防止批量替换吞掉标题——本轮就吞过一次「附录 A」标题）。
4. 交付时说明：最终文档的完整路径、按哪条仓库规则命名的、清理了哪些产物、清理后哪些引用被改写。

用户没表态 → 按默认（移动 + 保留全套 `.hdr-gate/`）执行，并在交付说明里点出「过程产物仍保留，要清理说一声」。

交付时告诉用户**四句话，第一句必须是评审强度**：

1. **这次的实际强度**：`review_mode` 是哪一级、审稿人真用了什么模型（跨族 / 同族多会话 / 单会话）、Agent4 归并是真跑了还是主持兼任、**作者与修复是 API 起草还是主持兼任（`AUTHORED-BY-HOST` / `FIXED-BY-HOST` 必须点名）**、假设有几条被真正核实过、以及**核实是谁做的**（审稿人若无文件读权限，必须说明事实核实由主持回仓库补做，并指出丢了什么）。**再加一句冷读强度**：双冷读里的 A 路（异族 API、无仓库权限）和 B 路（宿主侧只读 subagent、有仓库权限）**是否都真跑了**；只跑了 A，就要讲明白「文档对仓库的行号/签名/命令是否正确，没有第二双眼睛验过」。**这一句不许省，也不许含糊。**
2. 文档路径，以及它基于哪个 commit
3. 还有哪些 P2 未修、哪些 P1 转成了待办（在文档 §9）；**尤其要点名文档里是否有「开工前必须裁定」的假设清单（§1.4）**——那类条目一翻覆就作废整份文档，不能混在「已知限制」里让用户自己刨
4. 下一步：**开一个新会话**，把这份文档交给它执行；不要让写文档的这个会话自己执行（作者会脑补，文档的洞永远暴露不出来）

若强度低于 `full`，追加一句：补什么条件能重跑到 `full`、大约多少次调用。

**交付后停止。不要顺手开始写代码。**

## 成本与模型配置

| 配置 | 调用次数 | 场景 |
|---|---|---|
| 最小（一次通过、双冷读各 1 次） | 10 次 | 中等复杂 |
| 典型（1 轮返工 + 空正文重试 2 次） | **13–15 次** | 常规复杂需求 |
| 上限（2 轮返工） | ≈19 次 | 跨模块重构 |

**2026-10-26 全程实测量价（一次跨三个后端服务的真实需求，13 次 API 调用 + 1 个宿主 subagent 冷读）**：

| 阶段 | 模型 | 耗时 | 备注 |
|---|---|---|---|
| review 并行 | glm-5.3 + deepseek-v4-pro | 317s | glm 首跑返回 2 字节 → 作废 |
| review 重跑单角色 | glm-5.3 | 542s | 配额 32000 + 体量约束才拿到正文 |
| merge | qwen3.8-flash | 220s | 输入 3.8K / 输出 17K（思维链占大头） |
| sign 并行 | glm-5.3 + deepseek-v4-pro | 219s | 双签一次通过，无返工 |
| coldread | glm-5.2 | 292s → 0 字节；重跑 184s 成功 | 配额 20000 不够，40000 才收尾 |

**推理模型的输出配额一律别按「正文要多少字」估，要按「思维链 + 正文」估**：同一次调用 `out=17262` 里正文只占 3.8K，`out=27592` 里正文占 3.3K。**给审稿/签署留 32000、冷读留 40000，再用 prompt 里的体量硬约束把正文压到 2500 字以内**，两者缺一不可。墙钟时间按上表 ×1.5 预留，单角色重跑比整阶段重跑省一半。

| 角色 | 模型（默认走阿里百炼 Token Plan） | 模型族 | 备注 |
|---|---|---|---|
| Agent1 作者 | `qwen3.8-max` | qwen | 分析与长文档写作 |
| Agent2 可行性审 | `glm-5.3` | zhipu | 必须异族于 Agent1 |
| Agent3 正确性审 | `deepseek-v4-pro` | deepseek | 必须异族于 Agent1 |
| Agent4 合并去重 | `qwen3.8-flash` | qwen | 只归并，不定级 |
| 冷读试跑者 | `glm-5.2` | zhipu | 异族于 Agent1、未参与评审 |
| 主持 | 你自己 | — | 分级、裁定、版本管理 |

**异质性看「模型族」，不看「通道」。** Token Plan 一个通道里同时有 Qwen / GLM / DeepSeek 三家模型，`provider` 相同但族不同，盲区照样不重合。真正无效的是同族同模型——那只是换了会话，脑补习惯一模一样。`hdr.py doctor` 会按族判定并给出提示。

另外注意：三家挤在一个通道意味着单点故障，通道挂了双审同时失败。介意就给 agent1 配 fallback。

平台不支持指定具体模型时：用 lite 近似 flash、default/reasoning 近似 max，并靠**会话隔离 + 职责写死**保证独立性。

## 常见误用（自查表）

| 症状 | 问题 |
|---|---|
| 没做第 0 步判定就开写 | 轻量需求被上了重流程 |
| **先发澄清、等回答、再判定** | 两轮打断。判定不依赖细节，应先判定再合并提问 |
| **一次问超过 4 个问题，或选项没有默认值** | 把决策成本转嫁给用户；用户会答一半就烦了 |
| **问用户"你们接口怎么鉴权的"** | 仓库里查得到的事实不该问人，先读代码 |
| **假设只记在脑子里** | 阶段 2 无法打假，错假设一路带到定稿 |
| 两个审稿人看到对方清单 | 锚定，双审退化成一个审 |
| **同族两个会话，却说"已过双审"** | 只拿到会话隔离，没拿到盲区错开。必须降级标注为 `session` |
| **说"平台不能指定模型"，但没试过 `model` 参数** | Agent 工具支持 default/lite/reasoning，至少能拉尺寸差。先试再说 |
| **doctor 报缺密钥，看一眼就往下走** | 配置再漂亮也跑不起来。退出码 2 就是"不许继续" |
| **归并由主持兼任，交付时不说** | 漏并只有独立视角能捞回来，兼任必须声明 `MERGED-BY-HOST` |
| **把慢任务挪到后台，然后结束回合** | 后台完成通知只在下一回合到达，结束回合等于没人接收。必须同回合阻塞等待 |
| **一次吞 20 万字符上下文** | 单次调用可能 10–30 分钟，还吞不出更多有效信息。先切到 6–12 万 |
| 让 GLM/DS 当冷读者 | 它们已读过文档，是假装陌生 |
| 冷读时回答了它的提问 | 补的是对话不是文档，试跑作废 |
| 文档缺可执行验收断言 | 接手方必然卡住，等于没写 |
| 定稿后自己动手写代码 | 作者的脑补会让文档缺陷永远暴露不出来 |
| **以为「压上下文」能救 draft** | 真瓶颈是**输出长度**（一次生成整份长文档）非流式必超时。上下文压到 22K、`max_tokens` 降到 14000、`timeout` 提到 900s，照样 1000s 无响应。这三阶段交给主持写 |
| **产物是 0–2 字节空文件，判定「模型/通道不可用」** | 推理模型把 `max_tokens` 花在思维链上、`content` 返回空。先看 `progress.log` 的 `out=` / `reasoning=`，再抬配额 + 给 prompt 加输出体量硬约束 |
| **拿空清单往下跑 merge** | 空产物不报错就会静默污染归并与定稿。工具现已在各阶段落盘前校验非空+格式，但人工 spawn 时也要自己数一遍条数 |
| **要求 API 审稿人「到仓库核实假设」** | 它们没有文件读权限。核实必须由主持回仓库做并落 `resolution.md`；否则 P0 会建立在审稿人的推测上 |
| **冷读者带上作者的 recon.md** | 带着作者先验补课，缺口清单假性干净。冷读只给文档 |
| **只跑 API 那一路冷读就交付** | API 冷读者没有仓库读权限，报不出「文档对代码的行号/签名/命令是否成立」这类**事实性错误**——而这是接手方最容易撞的。必须双冷读（A 异族 API + B 宿主侧只读 subagent） |
| **用户已建好空占位文件，你却跑到第 8 步才落盘** | 中间几十分钟他看到的就是空文件，会问「怎么什么都没有」。双签通过即写交付路径，冷读补齐后再覆盖（铁律 9） |
| **把团队文档里的构建/生成命令照抄进 §1.2** | 基准环境常与本机不同（实测：文档要求某个基准容器，本机根本没起）。每条验收命令必须先在本机跑一遍，跑不通就写本机兜底路径或 §6.2 停止线 |
| **验收断言没标注「基线本来就是红的」** | 历史坏测试/历史 lint 错会让接手方以为是自己改坏了。实测过的失败原文直接抄进文档并写「期望：FAIL，基线既有状态，不要修」 |
| **手写临时 python 脚本调 `llm.chat` 重跑某角色** | 绕过 `require_artifact` 校验与 `add_cost` 记账，成本失真、空产物再次蒙混过关。用 `hdr.py retry --stage … --max-tokens …` |
| **双签通过后没同步 frontmatter** | 文件叫 v0.3、正文写 `doc_version: v0.2 / status: under-review`，接手方读到一对矛盾。`hdr.py sign` 已自动打戳，人工 spawn 时要自己改 |
| **审稿人的「非阻塞知会项」直接放过** | 它不挡签署，但会卡住冷读者与接手方（实测两处：内部矛盾 + 文件数漏算导致断言必不中）。修掉并在版本记录单列 |
| **doctor 报 agent1 无可用通道就降级为 `session`** | 那是 fallback 缺 key 的误报，角色链本身跨族。先 `heterogeneity` 直查族别再下结论（见第 -2 步） |
| **只在文档里给 `文件:行号`，要求执行者「逐字搬移」** | 搬什么？冷读头号缺口。要求照抄的对象必须整段内嵌 |
| **断言里写 `$(make_key)`、`/Users/xxx/python3.12`** | 命令不可原样执行 = 该卡没有验收 |
| **审稿人给的阻塞理由，用「加条停止线让执行者自己发现」应付** | 阻塞理由常指向方案缺陷（本轮：管道 role 会被静默绕过）。先回代码核事实，事实站它那边就改方案 |
| **`.hdr-gate/` 在错误目录里生成后到处找** | 它相对 cwd 落盘。所有命令固定在目标仓库根执行；工具会从登记簿找回并打印绝对路径 |
| **默认把 `<需求名>.md` 扔在仓库根，没问过项目规矩** | 多数团队有专门的需求文档目录（`openspec/specs/`、`docs/specs/`、编号或日期前缀）。**首次在本项目用本 skill 必须先问落点并按既有目录规则命名**，仓库根只是兜底 |
| **清理了过程产物，却留着文档里的自引用** | 接手方照着「见 `degraded.md` / `resolution.md`」去开文件——不存在。删产物必须同步改引用，并把执行期记录改指到 gitignore 的临时目录 |
| **先 `rm` 再移动文档** | 顺序反了就把交付物删了。永远：移动 → 校验字节数 → 再删 |

## 配套工具：优先用脚本驱动，别手工搬运

`tools/` 下有一套零依赖实现，把上面的阶段变成了可执行命令。**有这个目录就用它**，比手工 spawn 更快也不容易漏步骤。

### 若已挂载 MCP（`hdr-gate` 服务）

| 工具 | 用途 |
|---|---|
| `hdr_ask_parallel` | **双审就用它**：一次并行问 agent2 + agent3，两者互不可见 |
| `hdr_ask` | 单次按角色提问，可传 `repo` 自动附带文件树 |
| `hdr_list_roles` | 查模型绑定 + 异质性体检（同厂会标 ❌） |

### 若用命令行

```bash
python3 tools/hdr.py doctor                          # 先自检
python3 tools/hdr.py init --name X --repo /path --req "…"
python3 tools/hdr.py draft --name X                  # 阶段1
python3 tools/hdr.py review --name X                 # 阶段2（自动并行）
python3 tools/hdr.py merge --name X                  # 阶段3
python3 tools/hdr.py fix --name X                    # 阶段4
# 阶段5 人工裁定 → 写进 .hdr-gate/X/resolution.md
python3 tools/hdr.py sign --name X                   # 阶段6（解析 SIGNOFF）
python3 tools/hdr.py coldread --name X               # 阶段7
python3 tools/hdr.py finalize --name X               # 阶段8 → 交付
python3 tools/hdr.py status --name X

# 空正文/被截断时的正道（成本照常入账、落盘前照样校验）：
python3 tools/hdr.py retry --name X --stage review-a --doc v0.1.md --max-tokens 32000
python3 tools/hdr.py retry --name X --stage coldread --doc v0.3.md --max-tokens 40000
# stage ∈ review-a | review-b | merge | coldread
```

### 没有工具时

退回手工流程：用 Agent 工具 spawn 独立 subagent，把角色职责和输出格式写进 prompt（格式见 `tools/prompts.py`），产物落盘到 `.hdr-gate/<需求名>/`。
**最关键的一点不变**：两个审稿人的会话必须互不相通，冷读者必须是全新上下文。
